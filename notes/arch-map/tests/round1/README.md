## 怎么读这个结果

1. **落点题顶到了天花板。** 不给任何材料，读者也能在 89% 的题上说中被改的文件。模型对 PG 源码树的先验很强，L1 表里"哪个模块在哪个文件"对模型读者的增量很小。
2. **第二部分压在地板上。** 题目要求预测某个具体提交的缺陷或修法，答案取决于代码级的细节；L0/L1 层的抽象按设计不含这些细节。683KB 的 README 原文同样帮不上。
3. **地图有增益的地方是跨模块的不变量。** 得分提升最大的两题（B1-05、B3-05），读者都是靠卡片里一条跨模块规则推到了正确的风险类别。
4. **规则写得不全时会把读者带偏。** B3-03：不给材料的读者答对了，地图读者由 S07 的提交顺序推反了方向。可见性卡片当时只写了"先查进行中、再查 pg_xact"，没有写"判定中止不能用 DidAbort，只能用排除法"，也没有写它适用于所有代码路径。已补为 S06.M05 的 Inv(4)。
5. 三位地图读者都没有读 `principles.md`（只被 grep 扫到）。

## 方法

- **出题**：从 2026-07-01 之后、基线之前的提交里取，12 个子系统各 4 题；提交的 hash 不得在地图里出现过。只给意图或症状，不给文件名、函数名和修法。规范见 `scripts/DRAFT.md`。
- **读者**：sonnet，闭卷，只能读指定材料（`scripts/READER.md`）。每组 12 题一个读者。
- **落点**：机械评分（`scripts/score.py`），答案是提交实际改动的 `src/backend` 文件。
- **第二部分**：盲评（`scripts/GRADER.md`），评分员看不到条件标签，逐个要点给 0 / 0.5 / 1。要点是出题时从提交信息里逐字摘出来的。主线程抽看了两题的评分。
- 汇总：`scripts/agg.py`；逐题记录在 `grades/recs.json`。

## 这一轮量不到的东西（局限）

- **闭卷。** 地图的设计用途是"先读地图，再按需下钻代码"。这一轮没有量下钻：有没有少读代码、有没有少漏不变量。
- **读者只有一种模型。** 更强的模型先验更强，增益可能更小；更弱的可能更大。
- **地图建在这些提交之后。** 地图描述的是修复后的状态，对地图条件略有利。
- **评分员能从答案措辞看出条件**（答案里会出现"地图没写"之类的话），盲评不完全。
- **README 对照没有按 token 对齐**：给的是全部 40 个 README（683KB，地图是 436KB），读者自己选读。
- 分层曲线只在第 4 组做了 L0 一档。
