## B4-04
FILES: access/heap/visibilitymap.c, catalog/storage.c, access/heap/vacuumlazy.c, access/transam/xloginsert.c
ANSWER: When truncating the VM, always WAL-log the last remaining VM page after clearing its bits. Do this by writing a full-page image or log_newpage-style record, regardless of checksums and wal_log_hints, so the page LSN and a block-modified record come after the truncation. The incremental backup's block tracking (WAL summaries) then sees the VM block as modified and includes it. The truncation record alone is not enough, because it is older than the backup start LSN and is not replayed. Constraint: do not rely on hint-bit WAL logging, which is conditional (S06 Inv(3), S09 WAL-first rule).
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read visibilitymap_prepare_truncate and RelationTruncate (catalog/storage.c), and how walsummarizer or basebackup decides which blocks to include.

## B4-07
FILES: replication/walreceiver.c, replication/libpqwalreceiver/libpqwalreceiver.c
ANSWER: Changing the identify-system call's return value or signature alters the walrcv_identify_system entry in the WalReceiverFunctionsType function table, which is the libpqwalreceiver loadable-module interface. That is an ABI/API break and cannot be back-patched to released branches (S12 rule: minor releases do not change the ABI). So the fix adds a new, additive way to pass the flush position to the caller, and the walreceiver waits and retries before START_REPLICATION.

## B4-08
FILES: replication/logical/snapbuild.c, storage/ipc/procarray.c, commands/repack.c
ANSWER: When building the exported or initial snapshot, do not trust the decoder's committed list alone. Check each transaction in it against the live running set (ProcArray), or wait for it to finish, so one that has written its commit record but not yet its clog status is treated as in-progress (put into xip). Reason: MVCC visibility needs clog/ProcArray and WAL commit order to agree. S07 Inv(1): commit order is WAL, then clog, then ProcArray. A snapshot built from WAL-only commit state breaks it, and hint bits would be set wrongly.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read SnapBuildInitialSnapshot and SnapBuildBuildSnapshot in snapbuild.c, and TransactionIdIsInProgress in procarray.c.

## B4-11
FILES: commands/tablecmds.c, catalog/pg_constraint.c
ANSWER: Implicit child validation would turn ALTER CONSTRAINT ... ENFORCED into a full table scan of every child while recursing. ALTER CONSTRAINT is meant to be a metadata flip, with the scan as a separate VALIDATE CONSTRAINT step that takes a weaker lock (ShareUpdateExclusive) so that it does not block writes. Doing it implicitly would hold a stronger lock on the whole inheritance tree for a long time, and it would change semantics the user did not ask for. So the command raises an error with a hint to validate the child's constraint first.
CONFIDENCE: high for (a); medium for (b)
DRILL: Read ATExecAlterConstraintInternal and the recursion for ENFORCED in tablecmds.c.
