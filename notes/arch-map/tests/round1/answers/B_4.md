## B4-03

## B4-04
FILES: access/heap/visibilitymap.c, catalog/storage.c, access/heap/heapam.c, postmaster/walsummarizer.c, access/transam/xloginsert.c
ANSWER: In visibilitymap_prepare_truncate, when the last remaining VM page is cleared, always WAL-log it (log_newpage_buffer, a full-page image) even when checksums and wal_log_hints are off, instead of only dirtying it. Per the transam README, a change that is not WAL-logged is only a hint. This one must be durable, and the WAL summarizer only learns a block was modified from a block reference in WAL. Without a block reference, the incremental backup omits that VM page. The new record carries the VM block so the summarizer marks it modified. This happens inside the truncation critical section and fork-truncation ordering.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read visibilitymap_prepare_truncate and RelationTruncate (catalog/storage.c) for the XLogHintBitIsNeeded() conditionals.

## B4-08
FILES: replication/logical/snapbuild.c, storage/ipc/procarray.c, utils/time/snapmgr.c, access/transam/clog.c, replication/logical/reorderbuffer.c
ANSWER: When SnapBuildInitialSnapshot (or equivalent) builds the exported snapshot, it must not put a committed-list xid in the snapshot as committed unless the commit is complete in clog and the xid has left the ProcArray. Xids that are still in the ProcArray (commit WAL written, clog not yet updated) are instead listed as running in xip. The decoder's committed list is ordered by commit WAL, but ordinary MVCC visibility and hint-bit setting rely on clog and ProcArray state. Otherwise the snapshot treats the xact as committed while TransactionIdDidCommit() still says not committed, and tuple hinting wrongly marks it aborted.
CONFIDENCE: medium for (a); medium for (b)

## B4-09
FILES: access/common/toast_internals.c, access/heap/heaptoast.c, access/common/detoast.c, commands/indexcmds.c, catalog/index.c
ANSWER: Likely overlooked: code that opens a TOAST table's indexes assumed exactly one index and used the first one. REINDEX CONCURRENTLY leaves two indexes on the toast relation: old and new, with a failed or interrupted run leaving an invalid one behind. TOAST insert/fetch/delete could then use an invalid or not-yet-ready index (or only update one of them). Chunks go missing from the live index, or a failed reindex breaks later toast access. Violated: every toast chunk is findable through the valid index in use, and invalid indexes are ignored. Fix: toast_open_indexes picks the valid index and tolerates several.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read toast_open_indexes / toast_close_indexes (toast_internals.c) and the toast-index handling in index_concurrently_swap, plus the REINDEX CONCURRENTLY toast tests.

## B4-11
FILES: commands/tablecmds.c, catalog/pg_constraint.c, parser/parse_utilcmd.c, commands/typecmds.c, catalog/heap.c
ANSWER: Make ALTER CONSTRAINT ... ENFORCED raise an error with a hint when a child constraint (in the recursion) is already ENFORCED but NOT VALID. The hint tells the user to run VALIDATE CONSTRAINT on the child first. Implicit validation during recursion was not chosen, probably because validation is a full row scan that needs a different lock level (VALIDATE uses ShareUpdateExclusive, not the DDL lock held here) and may be slow or fail. It would also silently undo the user's deliberate NOT VALID choice on the child. Validation stays an explicit separate step; the parent must not become validated unless every child is valid.
CONFIDENCE: high for (a); medium for (b)
DRILL: Read ATExecAlterConstraintInternal / ATExecAlterCheckConstrEnforceability in tablecmds.c and the recursion on children.

## B4-12
FILES: catalog/namespace.c, access/transam/xact.c, storage/lmgr/predicate.c, utils/time/snapmgr.c, storage/ipc/ipc.c
ANSWER: In the backend-exit temp-relation cleanup (RemoveTempRelations), run the cleanup transaction without the session's default serializable read-only deferrable mode, for example by forcing a plain isolation level and deferrable off before StartTransactionCommand. No safe-snapshot wait occurs then. Interrupts are deliberately held off during exit cleanup, so the wait could not be made cancellable. The right fix is to avoid the wait entirely, because the cleanup transaction does not need a serializable snapshot. Per the SSI README, the DEFERRABLE wait applies only to SERIALIZABLE READ ONLY transactions.
