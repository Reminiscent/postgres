## B2-01
FILES: parser/parse_utilcmd.c, commands/schemacmds.c, tcop/utility.c, parser/parse_utilcmd.c
ANSWER: The old code stamped the new schema name into each element's unqualified RangeVar/object names. After dropping that, the elements are resolved only through search_path (or the schema check is skipped). That can break when the element's name resolves outside the new schema: temp objects, or a search_path override that does not put the new schema first. The violated property is that every element is created inside the schema being created, and consistently (reordered or cross-referencing elements resolve to the same object).

## B2-02
FILES: optimizer/plan/setrefs.c, nodes/nodeFuncs.c, parser/parse_jsontable.c, utils/adt/ruleutils.c, optimizer/prep/prepjointree.c
ANSWER: The PASSING values live in two places: the JsonExpr inside TableFunc (docexpr/passing_values) and a separate TableFunc.passingvalexprs list. Generic tree walkers and mutators and planner passes treated only one copy, or treated them inconsistently. These include expression_tree_walker/mutator, flatten/setrefs Var renumbering, SubLink to SubPlan conversion, and ruleutils deparse. The copy handed to the executor then keeps stale Vars, unconverted SubLinks or unadjusted varnos and params. Typical triggers are PASSING arguments that reference columns of other FROM items (lateral), or sub-selects, in a planned query. Result: wrong results, crashes or "variable not found in subplan target list". The violated property is that the two copies must stay semantically identical through all tree transformations.
CONFIDENCE: low for (a); low for (b)
DRILL: Look at the TableFunc handling in nodeFuncs.c walkers and mutators, in setrefs.c set_tablefunc_references, and at how parse_jsontable.c builds passingvalexprs.

## B2-04
FILES: parser/parse_jsontable.c, parser/parse_expr.c, parser/parse_clause.c
ANSWER: The already-transformed PASSING expressions get passed to transformExpr again, once per non-ordinality column's JsonFuncExpr. Re-analysis of an already-analyzed SubLink hits "unexpected non-SELECT command in SubLink", and other already-transformed nodes hit "unrecognized node type". The fix transforms the PASSING arguments only once, in the JSON_TABLE top level. It then reuses the transformed result for each column, for example by passing the transformed list/JsonExpr into the column transformation or building column expressions from the analyzed arguments. Analysis of a SubLink is not idempotent and must not run twice, because transformed trees are not valid input.
CONFIDENCE: medium for (a); medium for (b)

## B2-05
FILES: optimizer/path/joinpath.c, optimizer/path/joinrels.c, optimizer/plan/createplan.c, optimizer/util/placeholder.c, optimizer/plan/setrefs.c
ANSWER: Once the "PHV overlaps but is not contained" restriction was lifted, the PHV is evaluated in the outer (left) side of a nestloop. Other join methods (hash/merge), or a nestloop where the PHV ends up on the inner side or as a parameterized-path input, were still allowed to be built. For those the PHV cannot be computed below the join or passed as a NestLoop param. So the planner fails ("failed to assign all NestLoopParams to plan nodes", "variable not found in subplan target lists") or gets a wrong plan. The violated property is that every PHV is evaluated at the correct level and with correct nullingrels/outer-join semantics. The join-path generator must only allow join methods and paths that can supply the PHV.

## B2-06
FILES: optimizer/path/joinpath.c, optimizer/plan/createplan.c, optimizer/util/pathnode.c, executor/nodeMemoize.c, include-side nodes (plannodes) only if needed
ANSWER: Previously Memoize's cache-key equality and hash function came from the type's default (btree/hash opclass) equality. The fix makes Memoize use the operator actually used in the join clause. paraminfo_get_equal_hashops takes the clause's opno (commuted if needed) and finds its hash function in its hash opfamily. These operators are stored in the Memoize path/plan and used by the executor (hashfunctions/eqfunctions) for lookup. Constraint: the cache must treat keys as equal only if the join clause does. A coarser-than-clause equality (for example bytewise = on a nondeterministic collation, versus the type's collation-aware equality) merges distinct cache entries. If the clause operator is not hashable, Memoize is not used. This matches the recent commit "Fix Memoize using the wrong equality operator for cache keys".
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read paraminfo_get_equal_hashops in joinpath.c and the hashOperators setup in nodeMemoize.c/make_memoize.

## B2-07
FILES: optimizer/plan/analyzejoins.c
ANSWER: Skipping every RTE with securityQuals was not chosen because RLS/security-barrier views are common, and that would disable SJE too widely. Instead SJE now compares the two RTEs: it merges them only when securityQuals (and the related permission/checkAsUser information) are equal(). When they are, the quals are identical so nothing is lost. In the merge, the removed relation's security-qual-derived restrictions are handled (reused or kept) rather than dropped. If they differ, elimination is refused for that pair.

## B2-08
FILES: optimizer/plan/createplan.c, executor/nodeMemoize.c, optimizer/plan/subselect.c, optimizer/util/clauses.c, optimizer/plan/setrefs.c
ANSWER: The fix computes the Memoize node's keyparamids by walking the entire cache-key expressions to collect every PARAM_EXEC Param inside them (via a walker such as pull_paramids), not only top-level Params. PARAM_EXTERN params are excluded, because external and exec param ids are unrelated numbering spaces. The key params are then also treated as parameters of the Memoize subtree, so any change to them flushes the cache. The reasoning: the cache is valid only for outer values that are fixed under the key. A key expression of the form a+param loses information, so a param referenced in an inner filter must invalidate the whole cache. Params are therefore matched by Param id sets (chgParam intersect keyparamids), not by key equality.
CONFIDENCE: low for (a); medium for (b)
DRILL: Read make_memoize and keyparamids in createplan.c, and the chgParam handling in ExecReScanMemoize.

## B2-09
FILES: executor/execExpr.c, executor/execExprInterp.c, utils/adt/jsonpath_exec.c, jit/llvm/llvmjit_expr.c
ANSWER: The jump on NULL context item or path skips the EEOP_JSONEXPR_PATH step, which initializes the JsonExprState for the row (error/empty flags, result). The step that returns NULL, or the ON EMPTY/ON ERROR coercion, then runs with stale state left from a previous row or with uninitialized state. For example, after a row that raised an error or empty condition, a later row with NULL input can wrongly apply ON ERROR/ON EMPTY, or return the earlier row's result, or crash. The violated property is that each row's result depends only on that row's inputs. The fix resets the per-row state before the jumps, or makes the jump target initialize it, and handles JIT too.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read ExecEvalJsonExprPath, the jumps in ExecInitJsonExpr (execExpr.c), and the jsestate reset logic.

## B2-11
FILES: commands/trigger.c, utils/adt/ri_triggers.c, access/transam/xact.c
ANSWER: Resetting the counter to 0 and clearing the callback list at subtransaction end was not chosen. A subtransaction can legitimately start inside a firing loop (a trigger function with an EXCEPTION block), and zeroing would wrongly say that the enclosing loop is not active. That breaks the outer loop's batching and callbacks. The fix is to make the bracketing error-safe and scoped. Depth and callback list are saved per subtransaction (in trans_stack, or via PG_TRY/PG_FINALLY) and restored on subtransaction abort to the entry value. The subtransaction end therefore only drops the state it created.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read afterTriggerFiringDepth (or similar), AfterTriggerEndSubXact and the callback list in trigger.c, plus RI_FKey_check fast path in ri_triggers.c.

## B2-12
FILES: executor/nodeSubplan.c, executor/execAmi.c, optimizer/plan/setrefs.c, optimizer/plan/subselect.c
ANSWER: Each hashed-SubPlan reference rebuilds its tables when the shared planstate's chgParam shows a parameter change. The first ExecReScan clears chgParam, so the later references see no change and keep stale hash tables. The fix is on the executor side: each SubPlanState tracks for itself whether its parParam values changed (it remembers the values/a flag when it was built), or the rescan notification is propagated to all SubPlanStates of that subplan. Each reference then rebuilds independently of the shared planstate's chgParam. This is chosen because the references cannot have separate plan states. The planner shares one subplan and plan state, and duplicating the subplan is costly or not possible after planning, so the per-reference state has to carry the invalidation.
CONFIDENCE: medium for (a); low for (b)
DRILL: Read ExecScanSubPlan/buildSubPlanHash and ExecReScanSetParamPlan in nodeSubplan.c, and how chgParam is consumed in ExecReScan.
