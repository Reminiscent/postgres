## B4-03
FILES: access/transam/xlog.c, replication/slot.c
ANSWER: Inferred from S09.M02 Inv(10)(11) and S10.M05 Inv(1). At the end of the checkpoint, before KeepLogSeg and RemoveOldXlogFiles, the slot minimum required LSN is recomputed from the current slot values (ReplicationSlotsComputeRequiredLSN and the saved restart_lsn). The checkpointer no longer relies on the stale XLogCtl value or a snapshot taken at checkpoint start. The recompute needs slot locks, so it cannot run inside a critical section or while holding WAL locks. The recompute also has to come before the max_slot_wal_keep_size truncation and invalidation step.

## B4-04
FILES: access/heap/visibilitymap.c, catalog/storage.c, backup/basebackup_incremental.c, postmaster/walsummarizer.c, access/heap/heapam_handler.c
ANSWER: The fix is probably in visibilitymap_prepare_truncate. When bits are cleared in the last remaining VM page, always WAL-log that page (log_newpage_buffer, an FPI) in the same truncation. This applies even when checksums and wal_log_hints are both off, and the page is not logged conditionally on those settings. The summarizer then sees the VM block as modified in the incremental window, so the incremental backup includes that VM page and the cleared bits survive the restore. It needs no new record type and no change to the incremental-backup format, so it can be back-patched. The cost is one extra FPI per truncate.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read visibilitymap_prepare_truncate (the XLogHintBitIsNeeded condition) and RelationTruncate in catalog/storage.c, then the truncation_block_length handling in basebackup_incremental.c.

## B4-07
FILES: replication/walreceiver.c, replication/libpqwalreceiver/libpqwalreceiver.c
ANSWER: The walreceiver learns the upstream flush position from IDENTIFY_SYSTEM and waits and retries before START_REPLICATION. The libpqwalreceiver module loads dynamically, and walrcv_identify_system is a function pointer in the WalReceiverFunctionsType struct, which is an interface between separately built objects. Changing the call's signature or return value would break the ABI of existing walreceiver modules in minor releases. So the fix adds the information without changing existing signatures, probably a new callback or a new struct member. That is also why it can be back-patched. See S10.M03 and D-compat-by-release-class (small releases do not change the ABI).
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read walrcv_identify_system in walreceiver.h and libpqwalreceiver.c, and the startup path of WalReceiverMain before walrcv_startstreaming.

## B4-08
FILES: replication/logical/snapbuild.c, storage/ipc/procarray.c, replication/logical/logical.c
ANSWER: In the code that builds the initial or exported snapshot (SnapBuildInitialSnapshot), the snapshot must not treat a transaction as committed until its clog status is set. The fix is probably to check the committed-transaction list against the ProcArray or xid locks. For any xid still running in the ProcArray, wait for it to finish (XactLockTableWait) or otherwise keep the snapshot consistent. This works because commit order is WAL, then clog, then ProcArray removal (S07 Inv(1)). Once the xid leaves the ProcArray, clog is already set, so hint bits are correct. The xid cannot be hidden as in-progress, since its commit record precedes the consistent point and it will not be replayed.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read SnapBuildInitialSnapshot and SnapBuildExportSnapshot in snapbuild.c, then HeapTupleSatisfiesMVCC and the hint-bit setting for the xid-not-in-snapshot-but-not-committed case.

## B4-09

## B4-11
FILES: commands/tablecmds.c
ANSWER: Implicit validation of the child during recursion is not done because ALTER CONSTRAINT ... ENFORCED takes a lock level suited to a catalog change. Scanning a child's rows is a different job from the parent's catalog update. It needs the table scan and lock treatment of VALIDATE CONSTRAINT, which is a separate command with a lighter lock (ShareUpdateExclusiveLock). Doing it silently inside the recursion would add an unexpected expensive scan and a lock-strength change to every child. The child's constraint may also differ and be managed independently, so the user should validate it explicitly. The error with a hint (VALIDATE the child first) keeps the parent's validated flag from ever being set without all children being checked, and that flag is what constraint exclusion relies on.
CONFIDENCE: high for (a); medium for (b)
DRILL: Read ATExecAlterConstraint and ATExecAlterConstraintInternal/AlterConstrUpdateConstraintEntry in tablecmds.c, and the recursion into children for convalidated.

## B4-12
FILES: catalog/namespace.c, access/transam/xact.c, utils/time/snapmgr.c
ANSWER: The fix is in the exit-time temp cleanup (RemoveTempRelationsCallback in namespace.c, which runs in a transaction started during backend exit with interrupts held). That transaction is forced to use settings that cannot wait for a safe snapshot. That means non-serializable, non-deferrable, and not read-only, regardless of default_transaction_* GUCs. Alternatively it takes a snapshot that does not go through the serializable-deferrable wait. The reasoning: cleanup must not depend on session defaults. It must never block in an uncancellable wait, because interrupts are held and it runs in a critical exit path. It needs only to drop its own temp schema objects, so no serializable guarantee is needed.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read RemoveTempRelations and RemoveTempRelationsCallback in namespace.c (StartTransactionCommand, GetTransactionSnapshot, HOLD_INTERRUPTS), and the DeferrableSnapshot wait in GetSerializableTransactionSnapshot (predicate.c).
