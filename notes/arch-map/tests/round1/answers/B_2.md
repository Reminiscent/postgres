## B2-01
FILES: parser/parse_utilcmd.c, commands/schemacmds.c, tcop/utility.c, parser/parse_utilcmd.c
ANSWER: Previously the schema name was stamped into each element's RangeVar (unqualified names, and a check that any explicit qualifier matches the new schema). With that gone, elements rely on search_path alone, so objects (and the "CREATE specifies a schema different from the one being created" check) are no longer reliably tied to the new schema. Breaks when an element's name is unqualified (or a different explicit schema) and the search_path / current creation namespace differs from the new schema, e.g. with the schema name given via AUTHORIZATION default or a search_path change. Violated: every element must be created in the schema being created; a mismatched qualifier must be rejected.
CONFIDENCE: low for (a); medium for (b)
DRILL: read transformCreateSchemaStmtElements() and CreateSchemaCommand() in parse_utilcmd.c / schemacmds.c, and the old setSchemaName logic.

## B2-02
FILES: optimizer/plan/setrefs.c, nodes/nodeFuncs.c, optimizer/util/clauses.c, executor/nodeTableFuncscan.c, parser/parse_jsontable.c
ANSWER: The planner (and rewriter/tree walkers/mutators) processed the TableFunc's JsonExpr but not the separately kept PASSING value list (or processed them inconsistently), so the two copies diverged. Breaks when PASSING args need planner transformation: sub-selects/SubPlans, Params, Vars of outer joins or pulled-up subqueries, constant folding, set_plan_references var renumbering. Result: executor evaluates un-planned/stale expressions, "unrecognized node type", wrong results or crashes. Violated: all expression trees in a plan node must be visited by the same traversals and stay consistent.
CONFIDENCE: low for (a); medium for (b)
DRILL: grep TableFunc handling in expression_tree_walker/mutator (nodeFuncs.c) and set_plan_references for passingvalexprs.

## B2-04
FILES: parser/parse_jsontable.c, parser/parse_expr.c
ANSWER: PASSING arguments are transformed once into the JsonExpr and then the already-analyzed expressions were run through transformExpr again for each non-ordinality column's JsonFuncExpr, which fails on analyzed nodes (SubLink already converted to a SubPlan-ready form, unknown node types). Fix: analyze PASSING args once and reuse the already-transformed nodes for the column expressions (pass them down, or copy), never re-transform. Constraint: transformExpr only accepts raw parse nodes, and transformation is not idempotent. FOR ORDINALITY-only works because no column expr is built.
CONFIDENCE: medium for (a); medium for (b)
DRILL: read transformJsonTable / transformJsonFuncExpr and how the passing list is handled per column.

## B2-05
FILES: optimizer/path/joinpath.c, optimizer/path/joinrels.c, optimizer/util/placeholder.c, optimizer/util/relnode.c, optimizer/plan/createplan.c
ANSWER: Allowing the overlapping PHV only works if the PHV is evaluated in the nestloop's left input (outer side), but the code did not enforce that other join types/orderings or the right-hand side never get the PHV evaluation. Under some join orders (hash/merge join, PHV needed on the inner side, or parameterized paths/lateral refs) the planner can choose a plan where the PHV is computed at the wrong place, giving "failed to find plan"/ variable-not-found errors or wrong values. Violated: a PHV must be computed exactly once at its proper level, before use, with consistent nulling by outer joins.
CONFIDENCE: low for (a); low for (b)
DRILL: read the commit removing the PHV-overlap restriction and the joinpath.c / joinrels.c PHV checks around join_is_legal and add_paths_to_joinrel.

## B2-06
FILES: optimizer/path/joinpath.c, optimizer/plan/createplan.c, executor/nodeMemoize.c, optimizer/util/pathnode.c, optimizer/plan/setrefs.c
ANSWER: Memoize cache keys used the type's default equality/hash (type cache) instead of the join clause's own operator. Fix: record in MemoizePath/Memoize the actual equality operators (and hash functions, found from the clause operator's hash opfamily, with the clause collation) from the parameterized join clauses and use those in nodeMemoize.c for hashing and key comparison. Constraint: cache key equality must be no coarser than the join clause's, otherwise distinct outer values share an entry; if no hashable operator for the clause, no Memoize.
CONFIDENCE: medium for (a); high for (b)
DRILL: read paraminfo_get_equal_hashops in joinpath.c and ExecInitMemoize.

## B2-07
FILES: optimizer/plan/analyzejoins.c
ANSWER: Skipping SJE for every RTE with securityQuals was rejected because it would disable the optimization for the common case where both references carry identical RLS quals (same role/policy). Chosen: compare the two RTEs' securityQuals (equal(), with matching security levels) and merge only when they are identical; otherwise do not eliminate the join. Also the merged baserestrictinfo keeps the quals once, so no quals are lost.
CONFIDENCE: medium for (a); medium for (b)
DRILL: read remove_self_joins_one_group / the RTE comparison code in analyzejoins.c.

## B2-08
FILES: optimizer/plan/subselect.c, optimizer/plan/createplan.c, executor/nodeMemoize.c, optimizer/path/joinpath.c, optimizer/plan/setrefs.c
ANSWER: Memoize's keyparamids were counted as covered by the cache key for any Param found in the key expressions. Fix: count a Param as covered only when the whole key expression is that bare PARAM_EXEC Param; params merely buried in larger expressions (or elsewhere in the subplan) must remain in chgParam so a change flushes the cache. Also ignore PARAM_EXTERN params, since their numbers are in a different space than executor params. Constraint: the cache key value only distinguishes entries if it determines the param value; otherwise the param change must purge the cache (finalize_plan Memoize case / ExecReScanMemoize).
CONFIDENCE: low for (a); medium for (b)
DRILL: read the T_Memoize case in finalize_plan (subselect.c) and ExecReScanMemoize.

## B2-09
FILES: executor/execExpr.c, executor/execExprInterp.c, jit/llvm/llvmjit_expr.c, jit/llvm/llvmjit_types.c
ANSWER: The NULL-skip jumps bypass EEOP_JSONEXPR_PATH, which also initializes/resets per-row state (jsestate error/empty flags, result), so after a NULL context/path the later steps read stale state left by a previous row (or uninitialized state). Breaks when rows are processed in sequence and an earlier row hit ON ERROR/ON EMPTY or similar, then a NULL-input row follows; wrong ON ERROR/EMPTY handling or wrong result. Violated: per-row expression state must be reset for every evaluation. Fix: do the reset in a step that is not skipped, or make the jump target reset it.
CONFIDENCE: medium for (a); medium for (b)
DRILL: read ExecInitJsonExpr and ExecEvalJsonExprPath in execExpr.c / execExprInterp.c.

## B2-10
FILES: executor/nodeSort.c, optimizer/plan/createplan.c
ANSWER: Checking only that the output has one column is not enough: Datum sort supports exactly one sort key. A Sort with a single column but several sort keys (the same column sorted with different operators/collations, or ORDER BY x, x USING ...) wrongly used Datum sort and ignored the extra keys, giving wrong ordering. Fix: also require plannode->numCols == 1 (and keep other conditions such as no randomAccess-incompatible modes).
CONFIDENCE: low for (a); low for (b)
DRILL: read ExecInitSort's datumSort condition in nodeSort.c.

## B2-11
FILES: commands/trigger.c, utils/adt/ri_triggers.c, access/transam/xact.c, commands/tablecmds.c, executor/execMain.c
ANSWER: Resetting to zero is wrong because a subtransaction can be inside a legitimately active firing loop of an enclosing (sub)transaction level; zeroing would make that outer loop look inactive, and clearing the whole callback list would drop callbacks that the enclosing loop still needs. Instead: make the bracket error-safe (PG_TRY/PG_FINALLY or restore a value saved at subxact start) and make subtransaction abort restore the depth to the value recorded for that level and discard only callbacks registered in the aborted subtransaction (tagged by subxact/nest level).
CONFIDENCE: medium for (a); medium for (b)
DRILL: read AfterTriggerFiringDepth/afterTriggerInvokeEvents and AfterTriggerEndSubXact in trigger.c, and the RI fast path batching check in ri_triggers.c.

## B2-12
FILES: executor/nodeSubplan.c, executor/execExpr.c, executor/execProcnode.c, optimizer/plan/subselect.c
ANSWER: The shared planstate's chgParam is consumed by the first reference's rebuild (ExecReScan clears it), so other SubPlanStates never notice. Fix: make each hashed SubPlanState detect param changes independently (e.g. per-reference record of the relevant PARAM_EXEC values / own chgParam bit set that is cleared per reference) so every reference rebuilds its own hash tables, rather than depending on the shared planstate flag. Constraint: references must keep sharing one plan state (plan tree read-only, one init per plan_id), and the per-reference state is the only place that can track what it built.
CONFIDENCE: medium for (a); low for (b)
DRILL: read ExecScanSubPlan / buildSubPlanHash and ExecReScanSetParamPlan in nodeSubplan.c.
