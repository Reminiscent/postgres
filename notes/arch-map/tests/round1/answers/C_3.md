## B3-03
FILES: access/heap/heapam.c, access/heap/heapam_visibility.c, access/transam/multixact.c, utils/time/snapmgr.c, access/heap/heapam_handler.c
ANSWER: The fix is to replace "is the member still in progress?" tests on multixact members with ones that follow the real commit order. In the commit path the order is WAL, then clog, then ProcArray, so a member that is in the ProcArray but already aborted in clog is not a live updater. The code must look at clog status (did-abort or not-committed) before or in addition to the in-progress test.
A crashed updater is neither running nor committed, so the code treats the multixact as holding only lockers: HeapTupleSatisfiesUpdate and heap_update/heap_lock_tuple handle an aborted update member as "locked only", not TM_Updated. In multixact expansion, aborted updaters are dropped. This avoids creating a multi with two updating members and avoids a false concurrent-update result.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read MultiXactIdIsRunning, DoesMultiXactIdConflict, compute_new_xmax_infomask and the HEAP_XMAX_IS_MULTI branch of HeapTupleSatisfiesUpdate.

## B3-05

ANSWER: The deferred update was not applied reliably when the transaction ended abnormally. On abort the code still saw the backend as holding an XID, or applied the barrier too early or too late relative to AbortTransaction's cleanup, so it was deferred again or was never absorbed.

## B3-06

ANSWER: Part (b) asks about the rejected alternatives. Write and flush waits are floored by the replay position, so they also depend on replay, not only on the receiver. A "receiver is active when the wait starts" test is racy: the receiver can stop later, and a blocked recovery cannot restart it or recycle WAL, so pg_wal can fill.

## B3-07
FILES: access/transam/twophase.c, access/transam/xact.c, access/transam/xlog.c, storage/lmgr/proc.c, access/transam/clog.c
ANSWER: In FinishPreparedTransaction's abort branch, set the DELAY_CHKPT_IN_COMMIT bit in MyProc->delayChkptFlags, as the commit branch does. Hold it from before the abort record is inserted until after the clog abort is set (RecordTransactionAbortPrepared and TransactionIdAbortTree) and the critical section is done. It is cleared afterwards.
A checkpoint cannot then choose its redo pointer between "abort record in WAL" and "pg_xact updated". If it could, crash recovery would start after the abort record and would not replay the abort, so the 2PC state file would bring the transaction back as prepared. Ordinary aborts do not need this because their outcome is not durable-acknowledged, but ROLLBACK PREPARED is acknowledged and its state file must stay consistent with the outcome.
CONFIDENCE: medium for (a); high for (b)
DRILL: Read twophase.c RecordTransactionCommitPrepared versus RecordTransactionAbortPrepared for delayChkptFlags usage.

## B3-08
FILES: storage/lmgr/proc.c, storage/ipc/standby.c, storage/lmgr/lock.c, utils/adt/lockfuncs.c, storage/lmgr/deadlock.c
ANSWER: Make the waiter own the field. Reset waitStart to 0 when the waiter leaves the wait or begins a new one, on every exit path: in the grant path, in LockErrorCleanup for cancel, timeout and deadlock victim, and in the startup process's lock wait in standby.c. Store the new start time with an atomic write after clearing.
The waker (ProcWakeup) must not be the one clearing it, because its reset can race with the waiter's next store. The startup process on a standby uses the same path, so the old time is no longer shown through its next wait.

## B3-11
FILES: storage/aio/read_stream.c, access/heap/vacuumlazy.c, storage/buffer/bufmgr.c, commands/vacuum.c, storage/aio/aio.c
ANSWER: Recreating the stream mid-scan would mean throwing away its look-ahead state. That state is the queued blocks and already-started in-flight reads, the callback's private position in the block-number sequence, and the per-buffer data. The block-number callback is a one-way generator, so the new stream could not resume the sequence at the right point without a rewind facility.
Pinned buffers and in-flight I/O would have to be drained or handed over, which costs time during a failsafe whose purpose is to finish quickly. Simply dropping the strategy in the existing stream is simple and safe, at the cost of the two accepted side effects.
CONFIDENCE: high for (a); medium for (b)
DRILL: Read read_stream_* in read_stream.c (new function that drops the strategy) and where lazy_scan_heap's failsafe code calls it.

## B3-12
FILES: storage/aio/method_io_uring.c, storage/aio/aio_init.c, storage/aio/aio.c, storage/ipc/ipci.c, postmaster/postmaster.c
ANSWER: The postmaster owns the io_uring instances and the file descriptors, and shared-memory reinit created new rings without closing the old ones. The fix is to tear down the old rings explicitly (io_uring_queue_exit on each context) before re-creating them on a crash restart, through an explicit shutdown or cleanup hook in method_io_uring.c called from the reinit path.
Reason: the postmaster does not exit between restarts and does not run per-process exit callbacks, so nothing released the resources by itself. Each cycle leaked fds and locked memory until "Too many open files" or "Cannot allocate memory".
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read pgaio_uring_shmem_init and the AIO shutdown hook in method_io_uring.c, and the AIO cleanup call in the postmaster's reinit sequence.
