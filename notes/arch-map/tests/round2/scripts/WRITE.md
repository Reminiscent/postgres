正文用中文，平实、简洁；标识符、函数名、文件路径保留英文。

## 这个文件是做什么的

地图已有：`L0.md`（总图，§6 是不变量族的强制点矩阵）、`subsystems/<n>.md`（模块卡，逐条写了不变量 Inv 和 Contract）、`principles.md`（力、决策、原则）。
一轮检验（`notes/arch-map/tests/round1/README.md`，先读它的"结论"和"怎么读这个结果"两节）表明：
读者靠模块卡回答"这个改动会破坏什么"时，得分只有在卡片恰好写了一条**跨模块规则**时才提高；规则写得不全时反而会被带偏。
同一族的规则现在散在十几张卡片上，读者不知道该看哪几张，也看不到"过去的改动是怎么把它破坏掉的"。

所以这个文件要让读者做到一件事：**拿到一个改动，能判断它会不会破坏这一族不变量，以及该去检查什么。**
它是一个视图：规则的完整表述留在所有者卡片上，这里用引用；这里新增的信息是跨模块的顺序（协议）、按改动类型组织的检查单、历史 bug 类别。

## 文件结构（各节都要有；某节确实没有内容时写"无"并说明查过什么）

```
---
id: I<n>
type: invariant
depends: [L0, principles]
---
# I<n> <名称>

## 1. 不变量
一句话。然后一行"适用条件"：在什么配置或状态下这条不变量不适用或被有意放松（例如 unlogged 表、fsync=off、恢复期间、单用户模式……），每项带证据。

## 2. 由什么推出
由哪些决策推出，只列 `[[D-…]]` 和各自的一个短语，不复述决策内容。

## 3. 规则
本族的跨模块规则，一条一行，编号 `I<n>.R1`、`I<n>.R2`……。表格列：
| 编号 | 规则（一句话） | 所有者（强制点） | 其他参与方必须做什么 | 条件与例外 |
- 只收：跨两个以上模块才能成立的规则（rules 文件里 D1≥2 的），或者一个强制点、其他所有模块都依赖它的规则。单模块内部的规则不收（它们留在卡片上）。
- 同一条规则在多张卡片上各写了一部分的，合并成一条，"所有者"写真正的强制点 `[[Sxx.Myy]] Inv(k)`，其余写进"参与方"。
- 规则这一列要自己能读懂（读者不打开卡片也知道规则是什么），但不要把卡片里的细节和锚点搬过来；证据由所有者卡片负责。
- 如果 bug 类别或源码显示有一条本族的跨模块规则**没有任何卡片写**，照样列出，在"所有者"里写"卡片未写"，并给出源码或 README 的证据锚点。

## 4. 协议
本族里写不成一句话的多步顺序（例如提交的步骤顺序、改页面并写 WAL 的步骤、checkpoint、崩溃重置、失效消息的收发时点）。
每个协议：名称、编号的步骤（每步写谁做、做什么）、哪一步之后哪条规则才成立、顺序颠倒会怎样。带 `readme:` 或 `file:` 证据。没有就写"无"。

## 5. 并发与失败语义
error / crash / cancel / standby 四种情形下本族不变量如何保持，各一两句，指向 §3 的规则编号或卡片。卡片上写"未定义""未核实"的照实汇总，不要补编。

## 6. 改动检查单
按"你在改什么"组织，一条一行：
| 如果改动…… | 必须检查 | 对应规则 | 漏掉的后果 |
每一行都要能追到 §3 的一条规则，并且最好能追到 §7 的一个 bug 类别。这是本文件最重要的一节：写读者真的会做的改动
（"新增一种 WAL 记录""在持有 buffer 锁时调用可能出错的函数""给 catalog 加一个缓存"……），不要写空泛的提醒。

## 7. 历史 bug 类别
| 类别 | 触发它的改动 | 违反的规则 | 后果 | 例子 |
例子是 2–4 个 `commit:<hash>`（你核对过的），不贴提交原文。类别按"犯的是哪种错"分，不按目录分。
某个类别违反的规则不在 §3 里，说明 §3 漏了一条，回去补上。

## 8. 校验手段
现有的机械检查：断言、GUC（如 wal_consistency_checking、debug_discard_caches）、测试套件（isolation、recovery TAP、amcheck……）、工具。每项一行：它能查出本族的哪类违反、查不出什么。带证据。没有机械检查、只靠约定的规则，在这里列出来。

## 9. 后来的抽象改进
把本族里"靠约定"的东西变成"靠机制"的提交（例如引入 ResourceOwner、PG_FINALLY、统一的接口）。每项一行，带 `commit:`。查不到就写"未考证"。

## 10. 外部参照
取 GUIDE §8 表里本族一行的外部参照，不扩写。
```

## 写作标准

- GUIDE §3.1 的三个检验：必要（去掉它哪类题会答错）、不可推导、代码里拿不到。函数清单、结构体字段、README 的原样复述不过关。
- 一事一处：规则的细节和锚点在卡片上；这里引用。本文件自己负责的新事实（协议顺序、bug 类别、校验手段、卡片未写的规则）必须自带证据。
- 证据格式：`file:<相对仓库根的路径>:<行>`、`commit:<hash>`、`readme:<路径>#<小节>`、`url:<链接>`；引用地图节点用 `[[S07.M03]]`、`[[D-…]]`、`[[X12]]`、`[[I2]]`。
- 原因分三种，不混写：原始原因（引入时的提交或文档说的）、当前原因（今天的代码和文档说的）、假设（没有原文支持的推断，必须写"假设"）。不编造 rationale。
- 带条件的说法不能写成不带条件的。拿不准的写"未核实"。
- 不设篇幅目标：先保证读者能据此判断风险，再求简洁。
