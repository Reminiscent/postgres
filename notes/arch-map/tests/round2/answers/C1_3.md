## R3-01
FILES: access/gin/ginvacuum.c, access/gin/ginbtree.c, access/gin/gindatapage.c, access/gin/ginxlog.c
ANSWER: The root cleanup lock is taken only once VACUUM already knows there are pages to delete, so the leaf scan runs without it. In the shared-to-exclusive window a concurrent inserter can split or otherwise change the page, and the root can stop being a leaf. VACUUM then rewrites a page it examined under stale assumptions. It can treat a page that is no longer a leaf, or is already deleted or half-dead, as a leaf posting list, or miss items that moved to a new right sibling. Result: posting-tree corruption or dead TIDs left in the index, which breaks index/heap consistency and the lock protocol (I3). Fix is to recheck page state (leaf, deleted, items) after reacquiring the exclusive lock and retry or skip. This is inferred from the map, not verified.
CONFIDENCE: low for (a); low for (b)
DRILL: read ginVacuumPostingTreeLeaves and ginScanToDelete in ginvacuum.c, and the git log of ginvacuum.c after the root-cleanup-lock commit.

## R3-02
FILES: access/gin/ginfast.c, access/gin/ginvacuum.c, access/gin/gininsert.c, access/gin/ginutil.c
ANSWER: The original made cleanup serial with a heavyweight lock on the metapage and made VACUUM wait. It overlooked that the tail recorded at cleanup start can be changed under it. A concurrent cleaner, or the early-stopping autovacuum/ANALYZE path, can delete or recycle the pending pages up to the recorded tail. Alternatively VACUUM can finish and then see new pending entries containing TIDs it has already declared dead. Cleanup can then follow a stale or deleted page link, or it can return leaving dead TIDs in the pending list. Result: the index keeps references to TIDs that VACUUM recycles (visibility/consistency violation), or cleanup errors out. Fix is a recheck or handling of the stop condition and metapage state in ginInsertCleanup, in particular for the VACUUM and forced-cleanup path. This is a guess.
CONFIDENCE: low for (a); low for (b)
DRILL: read ginInsertCleanup in ginfast.c (the lock, stopSuffix/tail handling, forceCleanup) and its callers in ginvacuum.c.

## R3-03
FILES: commands/vacuumparallel.c, commands/vacuum.c, postmaster/autovacuum.c, access/transam/parallel.c
ANSWER: The cost-parameter sharing is set up in parallel context creation (the parallel_vacuum_init path), and the registered on_dsm_detach callback runs at detach. The original overlooked the lifecycle mismatch. Setup happens even when no workers are launched or when init fails or errors out. The callback or the leader's global pointer to the shared cost state can then be left dangling, or be reset at the wrong time. Likely conditions: error or abort, a second parallel vacuum in the same process, or a worker for a non-autovacuum vacuum. Consequences: a stale DSM pointer read by vacuum_delay_point or the SIGHUP update path (crash), or cost settings clobbered or not restored. Violates resource lifetime (I5) and cost-delay correctness. Fix is to set up or clear the state symmetrically and make the callback idempotent.
CONFIDENCE: medium for (a); low for (b)
DRILL: read parallel_vacuum_init, parallel_vacuum_end and the detach callback in vacuumparallel.c, plus the shared cost state handling in vacuum.c.

## R3-04
FILES: utils/time/snapmgr.c, storage/ipc/procarray.c
ANSWER: ExportSnapshot and ImportSnapshot assumed the primary snapshot layout: xip for top-level xids, subxip for sub xids, and suboverflowed meaning the subxid cache overflowed. On a standby (takenDuringRecovery) all xids are in subxip, xip is empty, and the overflow flag has a different meaning. Export therefore drops or mis-writes subxip when the flag is set, or does not carry takenDuringRecovery. Import then rebuilds a snapshot that omits in-progress xids. Their effects then look committed, or the sanity checks reject the file. Result: the imported snapshot differs from the exporter's, so visibility is wrong (I2). Fix is to export and import takenDuringRecovery and subxip correctly, and handle the layout in the import validation and ProcArrayInstallImportedXmin.
CONFIDENCE: medium for (a); medium for (b)
DRILL: read ExportSnapshot, ImportSnapshot and parseXidFromText in snapmgr.c, and the takenDuringRecovery branch in GetSnapshotData in procarray.c.

## R3-05
FILES: storage/ipc/procarray.c, utils/time/snapmgr.c
ANSWER: The fix changes the locking and ordering in ProcArrayInstallImportedXmin so the importer's xmin is published atomically with the source check. It takes ProcArrayLock (stronger, or held across both the check and the xmin store) and orders the writes with memory barriers. The constraint: ComputeXidHorizons scans the PGPROCs under a shared ProcArrayLock, and a backend clears its own xmin without a lock. VACUUM could scan the importer's slot before it is set and the source's slot after it is cleared. Visibility of the importer's xmin must therefore be ordered against the source's possible clearing. An alternative form is to install the importer's xmin first and then validate the source. This is reasoned, not read.
CONFIDENCE: medium for (a); low for (b)
DRILL: read ProcArrayInstallImportedXmin and ProcArrayInstallRestoredXmin in procarray.c, and the xmin protocol in transam/README (section "Interlocking Transaction Begin, Transaction End, and Snapshots").

## R3-06
FILES: access/transam/twophase.c, storage/file/fd.c, access/transam/xlog.c
ANSWER: Form: make the state-file write crash-safe and atomic, not a partial in-place write. CheckPointTwoPhase / RecreateTwoPhaseFile writes to a temporary name, fsyncs it, then renames it to the final name with durable_rename. A crash or concurrent base-backup copy then sees either no file or a complete one; a partial temp file is ignored because its name is not a valid xid. Reasoning: startup reads every pg_twophase file and treats a bad size as fatal. A checkpoint-written file is only a cache of WAL data, so replay can recreate it. Alternative form, less likely: tolerate or discard a bad file at startup when WAL still holds the state.

## R3-08
FILES: postmaster/datachecksum_state.c
ANSWER: Form: tighten the shared-memory state protocol, all under DataChecksumsWorkerLock. The "launcher running" flag is cleared only at the very end of the launcher's exit handling, and by the exiting launcher itself, so a new start cannot see "not running" while the old one is still cleaning up. A start also resets or consumes the abort-requested flag under the lock. A new start while an abort is still pending is rejected or waits until the abort has finished, so a stale abort does not kill the new run and the new run does not start before the old one is gone. Reasoning: shared flags that gate a single-instance process need an atomic check-and-set. Clear-on-exit ordering and a handshake for abort are needed.
CONFIDENCE: high for (a); medium for (b)
DRILL: read StartDataChecksumsWorkerLauncher, the abort path and the exit callback in datachecksum_state.c, and every use of launcher_running and abort_requested.

## R3-09
FILES: access/transam/xlog.c, access/transam/xlogrecovery.c, postmaster/datachecksum_state.c
ANSWER: Form: in the XLOG_CHECKPOINT replay code in xlog.c, stop adopting the checkpoint's data_checksum_version unconditionally. The online-change state changes (XLOG_CHECKSUMS records) are the only source of change during replay. The control file's value is kept, because offline pg_checksums changes only the control file on that node. The checkpoint's value is adopted only where the control file is untrustworthy: starting recovery from a base backup (backup_label), where the control file was copied at an arbitrary moment. There the state is taken from the backup's starting checkpoint, and the control file watermark skips stale migration records. Reasoning: the checksum state is per-node when changed offline, so WAL from another node must not overwrite it, except at the backup start where the node has no valid state.
CONFIDENCE: medium for (a); medium for (b)
DRILL: read the XLOG_CHECKPOINT_SHUTDOWN/ONLINE branch of xlog_redo, the backup_label setup in xlogrecovery.c and the checksum-state handling in StartupXLOG.
