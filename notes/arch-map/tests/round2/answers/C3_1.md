## R1-02
FILES: storage/ipc/shmem.c, storage/ipc/ipci.c, storage/ipc/dsm_registry.c, utils/mmgr/mcxt.c, tcop/postgres.c
ANSWER: Most likely the post-startup registration and processing of the callbacks is wrapped in PG_TRY/PG_CATCH (or an equivalent cleanup step). On error it resets the module-level state: the "registering" or "startup phase" flag, the pending-request array pointer and count, and the allocation bookkeeping. It then re-throws, which is required by I5.R1 (a PG_CATCH must re-throw or abort the transaction). Reason: ERROR is a longjmp and the session survives. Static state set up during the operation would otherwise outlive the memory context that held it (dangling pointers to freed request records) and stay in the wrong phase (so the next attempt takes the postmaster-startup path). This is the I5.R14 rule: state registered during an operation must be undone on every exit path. The main segment is never freed (S01.M03 Inv 1b), so the fix cannot roll back allocations. It only resets the local request bookkeeping.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read shmem.c and ipci.c, the post-startup request/init entry point and the static request-state variables, and check where the error paths leave them.

## R1-03
FILES: storage/ipc/shmem.c, storage/ipc/ipci.c, storage/ipc/shmem_hash.c
ANSWER: Add an explicit check in the late (post-startup) request/attach path of shmem.c. If the request carries the unknown-size marker and the ShmemIndex lookup finds no entry, return failure (NULL, or an ERROR "not found") instead of falling through to the create/allocate code. The marker must never reach the size arithmetic. Reason: -1 becomes a huge size_t, so add_size and the alignment arithmetic overflow and a bogus allocation corrupts shared memory. The main segment is a fixed-size region that is never freed (S01.M03 Inv 1 and 1b), and late requests only get a small margin. A bad allocation therefore cannot be undone, and the sentinel must be rejected before allocating. The startup path already handles it, so the post-startup branch should get the same treatment.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read the ShmemInitStruct and request-processing path in shmem.c for how SHMEM_ATTACH_UNKNOWN_SIZE is handled at startup versus after startup, and the size computation (add_size and overflow checks).

## R1-04
FILES: commands/async.c, lib/dshash.c, storage/lmgr/lwlock.c, utils/fmgr/funcapi.c, tcop/postgres.c
ANSWER: pg_listening_channels kept a dshash sequential scan open across SRF calls. A dshash_seq_search holds a partition LWLock between calls (and dshash_seq_term is never reached on early termination, e.g. LIMIT, a closed cursor or an error). An LWLock held while control returns to the executor and the client violates I3 and I5. Cancel/die are held off and the lock cannot be seen by deadlock detection (I3.R12, I5.R4). Other sessions doing LISTEN/UNLISTEN/NOTIFY block behind it, and the same session can self-deadlock if it touches the table before the SRF finishes. The scan state also leaks if the SRF is abandoned (the I5 resource lifecycle). Fix: in the first call, copy the session's channel names into a local list and release the scan, or read the backend-local listen list, so no shared-table lock or scan survives between calls.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read pg_listening_channels in async.c, its use of dshash_seq_init/next/term and funcctx, and whether the fix returns results from a list built in one pass.

## R1-05
FILES: commands/portalcmds.c, executor/spi.c, utils/mmgr/portalmem.c, tcop/pquery.c, tcop/postgres.c
ANSWER: Pin the freshly created portal (PinPortal) for the window between creation and start, i.e. around planning and executor startup in PerformCursorOpen and SPI_cursor_open_internal, and unpin it once the portal is started. A pinned portal cannot be dropped, so a CLOSE issued from user code during planning raises "cannot drop pinned portal" instead of freeing memory the creator is still using. The alternative, re-looking up the portal after planning, is invasive and cannot cover every caller. Constraint: user code can run arbitrarily at those points, so protection must work without the creator learning about the drop. Pinned portals must be unpinned before commit (S02.M05 Inv 5), and the pin must be released on the error path. Portal state is process-local, so no locking is involved.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read PortalDrop and the pin checks in portalmem.c, then PerformCursorOpen and SPI_cursor_open_internal for the window between CreatePortal and PortalStart.

## R1-07
FILES: storage/lmgr/lock.c, storage/lmgr/proc.c, storage/lmgr/deadlock.c, storage/lmgr/lmgr.c, access/transam/parallel.c
ANSWER: The original change assumed lock-group members never wait on each other's heavyweight locks. Several group-aware paths still treat the group as one entity: LockCheckConflicts and holdMask accounting by group, ProcSleep wait-queue insertion that lets a member jump ahead when the group already holds the lock, and the deadlock detector merging group members into one node. With the relation extension lock now conflicting inside a group, a member can block on a lock held by its own leader or sibling. That wait is then mis-handled: wrongly granted or queued, a missed self-edge in the wait-for graph, or an undetected deadlock/hang (for example the holder waits on the waiter through the parallel-query machinery). The property violated is I3.R12: waits among processes must be visible to deadlock detection, plus mutual exclusion of relation extension within a group. The fix adjusts lock.c, proc.c and deadlock.c so the extension lock is excluded from the group exemptions everywhere.
CONFIDENCE: medium for (a); low for (b)
DRILL: Read lock.c LockCheckConflicts, the lockGroupLeader branches in proc.c ProcSleep, and deadlock.c group handling, plus the follow-up commit after the PG13 extension-lock change.
