## R4-01
FILES: access/transam/xlog.c, storage/ipc/ipci.c, storage/ipc/shmem.c, access/transam/xloginsert.c, access/transam/xlogrecovery.c
ANSWER: Under EXEC_BACKEND a child re-execs and must re-attach to every shared structure (rerun request callbacks, attach_fn); init callbacks run only in the postmaster. A subsystem converted without a proper attach step (the old per-process ShmemInitStruct lookup, e.g. for XLogCtl or WAL-insert pointers) leaves the child's pointer or local state unset or NULL. With wal_debug=on the XLogInsert debug path touches that state, so the backend crashes or reads garbage. Violated: every process must see the same shared state, and EXEC_BACKEND builds must not diverge from fork builds.
CONFIDENCE: low for (a); low for (b)
DRILL: Read the commit that converted xlog.c to the callback API and its follow-up. Compare the attach/init callback registration against the old XLogShmemInit, and check which XLogInsert wal_debug code uses it.

## R4-02
FILES: commands/wait.c, access/transam/xlogwait.c, tcop/utility.c, access/transam/xlog.c, access/transam/xlogrecovery.c
ANSWER: WAIT FOR LSN only avoids holding a snapshot if none is already held. If it is issued inside a transaction block, with an isolation level at or above REPEATABLE READ, or in a transaction that already has an active or registered snapshot, the held snapshot still blocks replay and the self-deadlock returns. Or the timeout path (ms parsing, or wakeup versus sleep) hangs or is lost. The command must pop or refuse an existing snapshot (error out), and the wake-up and timeout handling must be correct. Violated: the wait must not block replay, and must end on LSN reached, timeout, or promotion.
CONFIDENCE: low for (a); low for (b)
DRILL: Read WaitStmt execution in commands/wait.c and ProcessUtility's snapshot handling for WaitStmt. Read the timeout and latch loop in xlogwait.c, and check git log for the fix touching them.

## R4-03
FILES: backup/basebackup_incremental.c, backup/walsummary.c, backup/basebackup.c
ANSWER: Fix is in the code that merges the per-summary block-reference data into one table (PrepareForIncrementalBackup). Summaries must be applied in strict LSN/TLI order. For each relation fork, the summary's truncation limit block must first be applied to the table accumulated from earlier summaries (dropping earlier block refs at or above the limit). Only then are that summary's own modified blocks added. The bug was that the limit was applied after, or independent of, adding the later blocks, so blocks re-extended and modified after truncation were lost. The reasoning: a limit block only invalidates references from before it, not those after it.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read the summary-reading loop in basebackup_incremental.c, with src/common/blkreftable.c (BlockRefTableSetLimitBlock and the entry merge) to see where the limit is applied relative to the block additions.

## R4-04
FILES: replication/walsender.c, storage/lmgr/condition_variable.c, replication/slot.c, access/transam/xlogrecovery.c, replication/walreceiver.c
ANSWER: A process can be on only one CV wait list at a time (cv_sleep_target). If the walsender calls any other CV sleep or cancel (slot acquire waits, ConditionVariableCancelSleep on an error or other path), it is silently removed from the wakeup list. Also, ConditionVariableBroadcast empties the list, so the walsender must re-register after each wakeup. A walsender that is not re-registered misses wakeups: it sleeps until its timeout, replication stalls or lags, and shutdown or logical decoding on a standby hangs. Violated: no lost wakeups (liveness) and timely WAL delivery.
CONFIDENCE: low for (a); medium for (b)
DRILL: Read WalSndWait/WalSndWakeup in walsender.c and ConditionVariablePrepareToSleep/Broadcast/CancelSleep in condition_variable.c. Check whether anything on the walsender loop cancels the sleep or leaves the list.

## R4-05

ANSWER: Enabling two_phase later has to be tied to the slot's two_phase_at point and to the subscription state (PENDING to ENABLED). The original change overlooked a state not covered, e.g. a subscription that is disabled, has tablesync workers or transactions already prepared before the switch, or a failure or restart in between. The catalog state (subtwophasestate) and the publisher slot can then disagree. A PREPARE is skipped or sent twice, and COMMIT PREPARED arrives without its PREPARE, or the data is applied twice or errors out. Violated: each transaction is applied exactly once, with no duplicate or missing data.
CONFIDENCE: low for (a); low for (b)
DRILL: Read AlterSubscription two_phase handling in subscriptioncmds.c, and the two_phase state transitions at the start of the apply worker in worker.c (including the tablesync READY check). Compare with the slot's two_phase_at in the walsender.

## R4-06
FILES: replication/logical/reorderbuffer.c, replication/logical/decode.c, replication/logical/snapbuild.c, replication/logical/logical.c, replication/logical/worker.c
ANSWER: The new clog-based "already aborted, so skip or truncate" check was applied to transactions that cannot be treated that way. Examples: a txn already being streamed or partly sent, a prepared txn awaiting COMMIT/ROLLBACK PREPARED, a subtransaction, or a txn whose xid is still running. Truncating its changes and bookkeeping (memory and size counters, invalidations, snapshots) then breaks the later abort, stream-abort or prepare handling, or the memory accounting. The result is assertion failures or crashes, or a wrong or missed stream-abort message sent to the subscriber. Violated: the reorder buffer's internal consistency, and that decoding output is correct for aborts.
CONFIDENCE: low for (a); low for (b)
DRILL: Read ReorderBufferCheckAndTruncateAbortedTXN in reorderbuffer.c and its callers (the large-txn eviction path). Check the txn flags (RBTXN_*) that it must not truncate, and what ReorderBufferTruncateTXN leaves behind.

## R4-07
FILES: access/common/tupdesc.c, optimizer/util/plancat.c, executor/execTuples.c, executor/execExpr.c, jit/llvm/llvmjit_deform.c
ANSWER: attnotnull now only says "a not-null constraint exists", but many places still treat it as "no NULLs exist". With NOT VALID, existing rows may hold NULLs. Optimizer proofs (outer-join removal, IS [NOT] NULL simplification, constant folding) and tuple deforming that skips the null-bitmap check or caches guaranteed-non-null columns (also JIT) then give wrong results. Examples: a NULL read as garbage, or rows wrongly eliminated. Only a VALID constraint (or the new-row enforcement) may be trusted for such proofs. Violated: query-result correctness (semantic equivalence) and tuple-access safety.
CONFIDENCE: low for (a); medium for (b)
DRILL: Grep the callers of attnotnull and the tupdesc nullability field (CompactAttribute / attnullability) in plancat.c, tupdesc.c, execTuples.c and llvmjit_deform.c. Check each uses the "valid" state rather than "exists".
