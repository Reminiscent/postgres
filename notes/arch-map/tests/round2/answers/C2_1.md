## R1-01
FILES: commands/vacuumparallel.c, commands/vacuum.c, postmaster/autovacuum.c, utils/misc/guc.c
ANSWER: The leader writes the throttling parameters into the DSM while helpers read them at their throttling checkpoints, apparently with no synchronisation. A reload mid-run can update the values while a helper reads, so it sees a torn or inconsistent mix of old and new settings (delay, limit, balance). Helpers can also keep stale values, or the autovacuum cost-balancing state is not shared correctly. Property violated: helpers must apply a consistent, current throttling configuration, so the cost-based delay limit is enforced correctly. Low confidence on the exact mechanism.
CONFIDENCE: medium for (a); low for (b)
DRILL: Read vacuumparallel.c (shared cost-delay params and the parallel_vacuum_update_shared_delay_params path) and the vacuum_delay_point caller in vacuum.c.

## R1-02
FILES: storage/ipc/shmem.c, storage/ipc/ipci.c
ANSWER: The registration state (pending request records and the "in startup" or "registering" flag) is not reset when an ERROR escapes. The fix wraps the processing in PG_TRY/PG_CATCH, or equivalent cleanup, so that on failure the static state is restored to "no pending requests" and the freed records are not reused. Constraint: the records live in a memory context that error cleanup frees. The state therefore has to be reset before or at the error, not left pointing at freed memory, and the backend has to stay usable after the error.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read the post-startup RegisterShmemCallbacks and ProcessShmemRequests paths in shmem.c, and how the pending-request list and flags are reset.

## R1-03
FILES: storage/ipc/shmem.c, storage/ipc/shmem_hash.c
ANSWER: In the post-startup request processing, an attach-only request (size SHMEM_ATTACH_UNKNOWN_SIZE = -1) whose structure is not found must not fall into the create path. The fix reports an error (ereport ERROR, or an explicit failure return) instead of allocating. Constraint: -1 is a marker, not a size. Adding it into the size arithmetic overflows, and a late (post-startup) allocation has only a small spare area.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read the attach-or-create branch of the shmem init-struct handling for late requests in shmem.c.

## R1-04
FILES: commands/async.c
ANSWER: The SRF kept a dshash sequential scan open across calls. dshash_seq_next keeps the partition LWLock held between calls, and the scan is not terminated if the query ends early or errors. So an LWLock is held while arbitrary executor code runs, and an error or abandoned query leaks it. The same session can then deadlock on its own lock, for example by doing LISTEN/UNLISTEN in the same query, and it blocks other backends. Property violated: LWLocks must not be held across SRF calls or user code (resource lifecycle and lock discipline). Fix: collect the channel names in one pass (first call or a local list), release the lock, then return the rows.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read pg_listening_channels in commands/async.c and the dshash_seq_init/next/term usage.

## R1-05
FILES: commands/portalcmds.c, utils/mmgr/portalmem.c, executor/spi.c, tcop/pquery.c
ANSWER: The fix pins the portal while it is being set up, using PortalPin/PortalUnpin, or an equivalent status guard, around planning and executor start in cursor open (PerformCursorOpen and SPI cursor open). A user command that tries to close it then fails with "cannot drop pinned portal" and does not free the memory. Constraint: portal memory is owned by the portal. The creator holds raw pointers across user-code execution and cannot be told about the drop, so the drop must be prevented, not detected afterwards.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read PerformCursorOpen in portalcmds.c, SPI_cursor_open_internal in spi.c, and PortalDrop and the pinning logic in portalmem.c.

## R1-06
FILES: utils/cache/plancache.c, utils/cache/inval.c, rewrite/rowsecurity.c, utils/cache/syscache.c
ANSWER: The fix registers syscache invalidation callbacks in plancache.c on the catalogs that RLS depends on: pg_authid, pg_auth_members and pg_database (owner change). A callback marks as invalid the cached plan sources that depend on RLS (the dependsOnRLS flag). The plan is rebuilt on next use, lazily. Constraint: these are not relation or OID dependencies recorded in relationOids/invalItems, so ordinary relcache invalidation never fires. The callbacks must be coarse (invalidate all RLS-dependent plans), since the key is not tracked per plan.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read PlanCacheSysCallback, CacheRegisterSyscacheCallback and the dependsOnRLS/rlsRoleId handling in plancache.c.

## R1-07
FILES: storage/lmgr/deadlock.c, storage/lmgr/lock.c, storage/lmgr/proc.c
ANSWER: Lock-group-aware code assumed that group members never block each other. The deadlock detector treats the group as one node, and LockCheckConflicts skips same-group holders. Once a relation extension lock does conflict inside the group, a member can wait on a relext lock held by another member of its own group, and the detector can miss that wait (a hang), or the conflict check or wait-queue ordering becomes wrong. Property violated: deadlock detection completeness and mutual exclusion of relation extension. The fix adjusted the group handling for the relext lock type. Low confidence on specifics.
CONFIDENCE: medium for (a); low for (b)
DRILL: Read the lock-group handling in LockCheckConflicts, ProcSleep and the wait-edge code in deadlock.c, including the LOCKTAG_RELATION_EXTEND exception.

## R1-08
FILES: utils/mmgr/dsa.c, utils/activity/pgstat_shmem.c, storage/ipc/dsm.c, lib/dshash.c
ANSWER: The no-OOM flag (DSA_ALLOC_NO_OOM) does not cover every failure path in dsa_allocate_extended. Needing a new DSM segment, dsm_create, can still raise ERROR (for example when DSM slots or segments are exhausted), and dshash can still fail elsewhere. An error then escapes while the half-built entry is still in the shared hash, so other backends crash on it. Property violated: a failed entry creation must never leave a partially initialised entry visible in the shared table, and failure should be a return value, not an exception. Fix: make segment creation honour the no-OOM request, and clean up in pgstat.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read dsa_allocate_extended and make_new_segment in dsa.c, dsm_create flags, and pgstat_get_entry_ref in pgstat_shmem.c.

## R1-09
FILES: utils/activity/pgstat_shmem.c, utils/activity/pgstat.c, utils/activity/pgstat_xact.c
ANSWER: Code that handled entries only through the single shared hash was not updated, or the kind-to-table mapping was wrong. Examples are shutdown stats-file write and read, reset and drop of all entries, entry-ref lookup, detach, and the kind loops at attach. Entries in a dedicated table, or kinds that are fixed-size with no table, were skipped or dereferenced as NULL. Likely consequences: custom-kind stats are not saved or restored, not reset or dropped, or a crash when a fixed-size kind is treated as having a hash. Property violated: every stats kind's entries are consistently found and managed whichever table they live in. Low confidence on which of these was the actual bug.
CONFIDENCE: medium for (a); low for (b)
DRILL: Read the per-kind table selection in pgstat_shmem.c (init, attach, pgstat_get_entry_ref), the stats-file write and read loops in pgstat.c, and the drop-all and reset-all functions.
