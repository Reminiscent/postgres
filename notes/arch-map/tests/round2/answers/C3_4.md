## R4-01
FILES: access/transam/xlog.c, access/transam/xloginsert.c, storage/ipc/ipci.c, storage/ipc/shmem.c, postmaster/launch_backend.c
ANSWER: The old ShmemInitStruct calls ran again in every EXEC_BACKEND child, and the same function body also set up process-local state. Examples are the local pointers into the shared struct and, under WAL_DEBUG, the per-process memory context or state used by wal_debug logging in XLogInsert. After the conversion only the init callback (postmaster only) and an attach callback exist. This local setup was not moved into the attach callback, so exec'd children never run it.
With wal_debug=on in an EXEC_BACKEND build, the debug path in XLogInsertRecord uses an uninitialized (NULL or stale) context or pointer in each backend. That crashes or asserts inside the WAL-insertion critical section, so it becomes PANIC and a whole-cluster crash reset. Property violated: I7.R6 and the S01.M03 contract that every child must redo per-process setup and re-attach in EXEC_BACKEND, plus I1.R2 (critical-section discipline for WAL insertion).
CONFIDENCE: low for (a); low for (b)
DRILL: Read the new attach-callback registration in storage/ipc/shmem.c and the XLOGShmemInit/XLOGShmemAttach split in access/transam/xlog.c. Look for the WAL_DEBUG code that creates walDebugCxt or a similar context, and for what the old foundXLog path did per process.

## R4-02
FILES: commands/wait.c, access/transam/xlogwait.c, tcop/utility.c, access/transam/xact.c, access/transam/xlog.c
ANSWER: The waiter lifecycle and the timeout handling were wrong. The waiter sits in the shared pairing heap (S09.M11 Inv(3), I5.R14) and must be removed on every exit path: timeout, cancel, error, abort, and end of recovery. The timeout is in ms and is converted for WaitLatch, with the deadline recomputed on each loop.
A timeout or error path that leaves a stale heap entry, or a ms-to-us overflow or negative-timeout case, gives a hang or a stale waiter. A later wake-up then dereferences a dead PGPROC (I5.R14, I3.R17). The other hazard is a snapshot still held in the caller (a transaction block, REPEATABLE READ, or a function call). That snapshot pins xmin, so replay is blocked or conflicting queries are cancelled. This violates the "wait without holding a snapshot" premise and I2.R16.
CONFIDENCE: low for (a); low for (b)
DRILL: Read WaitForLSN in xlogwait.c and ExecWaitStmt in wait.c. Check timeout arithmetic, the cleanup in every return path, and whether a held snapshot is rejected.

## R4-03
FILES: backup/basebackup_incremental.c, backup/walsummary.c, postmaster/walsummarizer.c
ANSWER: The summaries were merged into one block-reference table without keeping LSN order. The truncation "limit block" from a later summary was then applied to everything, including blocks modified after the truncation (the relation was extended again). Those later modifications were dropped, so the incremental backup left blocks out.
The fix processes the summary files covering the backup range in LSN order. A truncation limit is applied only to references accumulated from earlier summaries, and then the current summary's own block references are added. Constraint: a truncation record only invalidates earlier block references, never later ones. This is the I2/I1 requirement that the backup's changed-block set must stay complete (S09.M09 Inv(3)).
CONFIDENCE: medium for (a) (the shared blkreftable.c is in src/common, outside src/backend); medium for (b)
DRILL: Read PrepareForIncrementalBackup in basebackup_incremental.c and the BlockRefTable reader and limit-block handling in src/common/blkreftable.c.

## R4-04
FILES: replication/walsender.c, storage/lmgr/condition_variable.c, replication/slot.c, access/transam/xlogrecovery.c, replication/walreceiver.c
ANSWER: A process can be on only one condition variable's wait list at a time (S01.M05; ConditionVariablePrepareToSleep cancels any previous registration). The walsender registers on the shared "physical" or "logical" CV without sleeping on it. Any other CV sleep in the same process then silently removes it from the walsender CV's list. Examples are slot acquisition waiting on a slot's active CV, or WaitLSN/syncrep paths. Likewise a ConditionVariableCancelSleep on the abort or error path deregisters it.
After that, ConditionVariableBroadcast after WAL replay or flush no longer sets that walsender's latch. The walsender sleeps until its timeout or the next unrelated wake-up. This means stalled or delayed replication and logical decoding on a standby (a lost wake-up), a violation of I3.R17 (the wake protocol).
CONFIDENCE: low for (a); medium for (b)
DRILL: Read the walsender wait loop (WalSndWait) and its PrepareToSleep and CancelSleep placement. Read ConditionVariablePrepareToSleep for cv_sleep_target handling, and the broadcast call sites in xlog.c, xlogrecovery.c and walreceiver.c.

## R4-05
FILES: commands/subscriptioncmds.c, replication/logical/worker.c, replication/logical/tablesync.c, replication/slot.c, replication/walsender.c
ANSWER: The subscription catalog (subtwophasestate) change is transactional and MVCC-rolled-back. The slot change on the publisher (ALTER_REPLICATION_SLOT two_phase) is not transactional (S10.M15 Inv(2), I1). A rollback of the ALTER, a failure after the remote call, or running it inside a transaction block leaves catalog and remote slot disagreeing. Also, the running apply or tablesync workers keep the old two_phase state (S10.M13 Inv(6)/(7), I4.R9) until a restart.
Possible results are duplicate data, or a COMMIT PREPARED arriving with no matching PREPARE ("empty prepare"). The two_phase state is also checked non-atomically against pending prepared transactions and table sync state (a race). Property violated: apply consistency and exactly-once apply (I1/I4).
CONFIDENCE: low for (a); low for (b)
DRILL: Read AlterSubscription's two_phase branch and the PreventInTransactionBlock conditions. Read how the worker re-reads MySubscription and restarts, and the slot-side two_phase_at logic in slot.c/walsender.c.

## R4-06
FILES: replication/logical/reorderbuffer.c, replication/logical/decode.c, replication/logical/snapbuild.c, replication/logical/logical.c, access/transam/transam.c
ANSWER: The clog lookup truncates the transaction's changes but not everything that depends on them. Stale accounting and state can remain: the memory size counters (txn->size, rb->size), the txn flags, the base snapshot and oldest-xmin that drive catalog_xmin (I2.R14), and the streamed/spilled/prepared state. A partially streamed or prepared txn also needs a stream-abort or prepare-abort message, and the later abort record must still be handled.
Consequences are assertion failures or wrong eviction, a catalog_xmin held back or advanced wrongly, or the downstream never being told to discard already-streamed changes. The lookup must follow I2.R2: only "aborted" from clog is a permanent fact, and in-progress or crashed xids cannot be told apart by it. Property violated: I2 (visibility/catalog_xmin) and I5 (memory bookkeeping).
CONFIDENCE: low for (a); low for (b)
DRILL: Read ReorderBufferCheckAndTruncateAbortedTXN and its callers in the eviction path (ReorderBufferCheckMemoryLimit), and what ReorderBufferTruncateTXN resets compared with ReorderBufferCleanupTXN.

## R4-07
FILES: access/common/tupdesc.c, utils/cache/relcache.c, optimizer/util/plancat.c, executor/execTuples.c, commands/tablecmds.c
ANSWER: attnotnull now only means "a not-null constraint exists", but readers of attnotnull or the cached tupdesc nullability still treat it as "no row has NULL". An invalid (NOT VALID) constraint can sit on a table whose old rows contain NULLs. Optimizations that assume NOT NULL are then wrong: the planner's NullTest and IS NULL simplification, NOT IN to anti-join (I6.R2), and tuple deforming that skips null-bitmap checks or uses cached fixed offsets (attcacheoff/guaranteed-not-null columns), including the JIT path.
Results are wrong query results, or garbage and crashes when deforming rows that actually contain NULLs. The cached state must distinguish valid from invalid (relcache attnullability) and be invalidated when the constraint is validated (I4.R3). New rows are still checked on write.
CONFIDENCE: low for (a); high for (b)
DRILL: Grep for attnotnull and CompactAttribute attnullability uses in plancat.c, tupdesc.c, execTuples.c and execExprInterp/llvmjit_deform. Check how relcache fills the nullability.

It must lock the referenced grantor role (AccessShareLock) and re-check it still exists, and DROP ROLE must lock and re-check.
