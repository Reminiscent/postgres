## R3-01
FILES: src/backend/access/gin/ginvacuum.c, src/backend/access/gin/gindatapage.c, src/backend/access/gin/ginxlog.c, src/backend/access/gin/ginbtree.c
ANSWER: The shared-lock to exclusive-lock trade-up has a window with no lock held (I3.R11: state read before re-taking a lock must be rechecked). The cleanup lock on the root is only taken once there are pages to delete, so before that a concurrent inserter can change the page in the window. Likely case: the page (possibly the posting-tree root, which can start life as a leaf) is split by an insert, so it is no longer a leaf, or its content or right-link differs. VACUUM then runs leaf-vacuum or page-deletion logic on a page that is now internal or already changed. That corrupts the posting tree, produces wrong or lost TIDs, and breaks the lock protocol that was meant to prevent deadlock and concurrent modification. Fix: after getting the exclusive lock, recheck that it is still a leaf and still the expected page, else redo or skip.
CONFIDENCE: low for (a); medium for (b)
DRILL: read ginvacuum.c (ginVacuumPostingTreeLeaves, ginScanToDelete, and the lock upgrade) and gin/README section on VACUUM and concurrency

ANSWER: The cleanup callback is tied to DSM detach and registered when the parallel context is created (I5.R15). I suspect the shared cost-parameter setup and its detach callback fail to cover every path. The callback is registered before the shared state is set up, or it also runs in workers, or it runs when no workers were launched or on error/abort paths. ## R3-05

ANSWER: The fix is in ProcArrayInstallImportedXmin (procarray.c), with a matching change in snapmgr.c's ImportSnapshot. It orders the two steps so one of the backends is always visible to ComputeXidHorizons. The importer first publishes its own MyProc->xmin (with a memory barrier or under the right lock), then rechecks that the source backend's vxid and xmin still match, and errors out if not. The constraint is I2.R6, the horizon must be a lower bound of all possible snapshots. The alternative (a heavier exclusive ProcArrayLock) is less likely given the cost, so the answer rests on a publish-then-verify handshake.

## R3-06
FILES: src/backend/access/transam/twophase.c, src/backend/access/transam/xlog.c
ANSWER: In twophase.c, startup tolerates a damaged pg_twophase file instead of failing. If a state file has a bad size, is empty, or is truncated (or its CRC is wrong), recovery ignores it and relies on the PREPARE record in WAL, possibly removing the file. This is safe because the state file is only a copy of WAL content made at checkpoint (I1.R8, S07.M01 Inv 11), and a file damaged mid-write means the checkpoint did not complete (or a backup is restoring from backup_label). Redo therefore starts before the PREPARE record, and WAL replay recreates the state. The alternative of writing atomically with a temp file and durable_rename cannot cover files copied by a base backup, so tolerant reading on the read side is the likelier design.
CONFIDENCE: medium for (a); medium for (b)
DRILL: read restoreTwoPhaseData, ProcessTwoPhaseBuffer, ReadTwoPhaseFile and RecreateTwoPhaseFile in twophase.c, and CheckPointTwoPhase

## R3-07

ANSWER: The change is local to the launcher/worker code. (1) The launcher marks the shared catalogs as done only when the worker reports success, not at the moment it hands them out. If the first worker fails (database dropped), the shared catalogs stay pending and the next database's worker takes them. ## R3-08
FILES: src/backend/postmaster/datachecksum_state.c
ANSWER: The fix is in the shared-memory state handling of datachecksum_state.c. Everything the launcher exit callback does (clearing launcher_running, resetting the abort request, resetting the operation state) happens in one critical section under DataChecksumsWorkerLock, as the very last step of the exit callback. A starter checks and sets launcher_running under the same lock and refuses or waits while the previous launcher is still exiting. A start/abort/start sequence must not have the new start's state wiped by the old launcher's cleanup, or its abort flag consumed by the wrong instance. The abort flag is cleared only once the abort has fully completed. The constraint is process robustness and lock-protected shmem state (I7, I5.R14), since the launcher's exit path can run in a state that is not cancellable.
CONFIDENCE: high for (a); medium for (b)
DRILL: read the launcher entry and exit callback, StartDataChecksumsWorkerLauncher, and the abort handling in datachecksum_state.c

## R3-09
FILES: src/backend/access/transam/xlog.c, src/backend/access/transam/xlogrecovery.c, src/backend/postmaster/datachecksum_state.c
ANSWER: In the redo of checkpoint records, the data checksum state in the record is no longer adopted unconditionally. The control file (pg_control) is authoritative, since an offline pg_checksums change alters only the local node (S08.M12 Contract). Replay applies the checkpoint's value only where valid: when it is part of an online transition (the XLOG_CHECKSUMS records, with a control-file watermark to skip records covered by an offline change), or, for a base backup restored from backup_label (control file copied at an arbitrary time), until the backup end or consistency point. Otherwise a mismatch is ignored or flagged. The constraint is I1.R26 and I8.R12: checksum state is a cluster-local on-disk format marker and must not change from replay alone.
CONFIDENCE: medium for (a); low for (b)
DRILL: read the XLOG_CHECKPOINT_SHUTDOWN/ONLINE redo branch in xlog.c (xlog_redo), the data_checksum_version handling in StartupXLOG, and the backup_label/control-file adoption logic in xlogrecovery.c
