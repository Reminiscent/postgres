## R3-01
FILES: access/gin/ginvacuum.c, access/gin/ginbtree.c, access/gin/gindatapage.c, access/gin/ginxlog.c, access/gin/ginget.c
ANSWER: The share-to-exclusive lock trade on a posting-tree leaf is not atomic. In the unlocked window a concurrent inserter can split the page. The root can also be that leaf, so a root split turns it into an internal page. VACUUM then rewrites or deletes from a page whose state differs from what it examined. The cleanup lock on the root is taken only when pages are to be deleted, so it does not cover this window. Fix: recheck the page after re-locking, for example that it is still a leaf. Violated: index and posting-tree structural integrity (stale decision applied, possible corruption or lost entries, wrong index results). This is mostly inference from the map, which only says VACUUM takes a root cleanup lock to stop concurrent inserts (S06.M13 Inv 3).
CONFIDENCE: low for (a); low for (b)
DRILL: Read ginVacuumPostingTreeLeaves() and ginScanToDelete() in ginvacuum.c, and the git log of ginvacuum.c after the deadlock fix.

## R3-03

ANSWER: The cost-parameter sharing is set up at parallel-context creation and cleaned up by an on_dsm_detach callback. Likely overlooked: the callback and the process-local pointers to the shared cost state (and the autovacuum worker's own cost globals) can run, or stay live, in the wrong situation. Examples: the DSM detaches on error or when the context is destroyed while the leader keeps using the pointers; a worker that is not an autovacuum worker, or a context that was never fully set up, runs the callback. Result: dangling-pointer access or wrong cost balance. Violated: resource lifecycle (DSM-detach cleanup safety) and cost-based delay accounting. This is inferred from the question text, not from the map.
CONFIDENCE: low for (a); low for (b)
DRILL: Read parallel_vacuum_init()/parallel_vacuum_end() in vacuumparallel.c, the detach callback, and the git log for the autovacuum parallel-index commit.

## R3-04
FILES: utils/time/snapmgr.c, storage/ipc/procarray.c
ANSWER: The export file carried xmin, xmax, xip and subxip but not the snapshot's takenDuringRecovery flag. The map records the standby layout: everything in subxip, xip empty, and suboverflowed meaning something else (S07.M05 Inv 6-7). On import, a standby-taken snapshot is treated as a primary-style snapshot, or the other way round. Import-time sanity checks and visibility checks (XidInMVCCSnapshot) then apply the wrong rule. In-progress transactions can be judged not running, so uncommitted rows become visible. Or, if suboverflowed is misread, xids are looked up in pg_subtrans wrongly. Fix: export and import takenDuringRecovery and suboverflowed, and adapt the validation. Violated: snapshot visibility (MVCC) correctness.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read ExportSnapshot() and ImportSnapshot() in snapmgr.c (xcnt/subxcnt/suboverflowed checks) and XidInMVCCSnapshot().

## R3-05

ANSWER: The fix is in ProcArrayInstallImportedXmin: close the window between verifying the source and publishing the importer's xmin. Either hold ProcArrayLock in a mode that excludes ComputeXidHorizons while the importer reads the source's xmin and installs its own, or publish the xmin first and then re-verify, as GetSnapshotData does. ## R3-06
FILES: access/transam/twophase.c, access/transam/xlogrecovery.c
ANSWER: Make recovery tolerate bad state files, or make the write atomic. A crash mid-checkpoint means that checkpoint did not complete, so pg_control still points at the earlier redo point. WAL replay therefore still contains the PREPARE records and can rebuild the same state. In restoreTwoPhaseData/ProcessTwoPhaseBuffer, an empty, short or CRC-bad file can then be ignored (or removed) instead of failing with "incorrect size of file". The same reasoning covers a backup that copied a half-written file, since replay starts at the backup_label checkpoint. The alternative is to write to a temp file and durable_rename it. The constraint is that the file is a redundant cache of WAL content (S07.M01 Inv 11), not the sole source of truth.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read restoreTwoPhaseData(), ProcessTwoPhaseBuffer(), ReadTwoPhaseFile() and CheckPointTwoPhase()/RecreateTwoPhaseFile() in twophase.c.

## R3-07
FILES: postmaster/datachecksum_state.c
ANSWER: Two fixes in the launcher. (1) Mark the shared catalogs as done only after the first worker has actually completed successfully. If its database was dropped or the worker failed, leave them not-done and hand them to the next worker or retry, so a successful end state cannot skip them. (2) When waiting for temp-table owners, count only relations that have storage (exclude relkind view and other storage-less temp objects), because a temp view has no pages to checksum. Constraint: "success" must imply every page, including shared catalogs, was rewritten (S08.M12 Inv 3), and the wait must cover only objects that matter.

## R3-09
FILES: access/transam/xlog.c, access/transam/xlogrecovery.c, postmaster/datachecksum_state.c, access/transam/xlogbackup.c
ANSWER: Stop unconditionally adopting the checkpoint's data_checksum_version on replay. Adopt it only when the record reflects an online transition that the control file has not already overtaken. The existing mechanism is a control-file watermark that skips transition records already covered by an offline change (S08.M12 Contract). Otherwise keep the local control-file state, which is the node's own truth after offline pg_checksums. Special case: when starting from a base backup (backup_label present), the copied control file was captured at an arbitrary moment, so take the state from the backup's start checkpoint. Constraint: offline pg_checksums changes only the local node and must survive replay.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read the XLOG_CHECKPOINT_* redo branches in xlog_redo() and the XLOG_CHECKSUMS handling in xlog.c, plus the StartupXLOG backup_label path in xlogrecovery.c.
