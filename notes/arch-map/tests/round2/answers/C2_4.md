## R4-01
FILES: access/transam/xlog.c, storage/ipc/ipci.c, storage/ipc/shmem.c, access/transam/xloginsert.c
ANSWER: The old XLOGShmemInit ran in every EXEC_BACKEND child. Under WAL_DEBUG it created the per-process "WAL Debug" memory context, which is exempt from the no-palloc-in-critical-section rule. The new API runs init_fn only in the postmaster. Children run only attach callbacks, and none was added for this per-process state. So with wal_debug on in an EXEC_BACKEND build, the context is NULL or missing in child backends. XLogInsertRecord then pallocs its debug message inside the critical section. That trips an assertion or ERROR, which becomes PANIC. The property broken is that WAL insertion in a critical section must not allocate or fail. Per-process local state needs re-creating in each child, not just shared-memory init.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read the WAL_DEBUG block in XLogInsertRecord and where walDebug* is created (XLOGShmemInit or its attach callback) in xlog.c; check the git log for the follow-up.

## R4-02
FILES: commands/wait.c, tcop/utility.c, access/transam/xlogwait.c, tcop/pquery.c, parser/gram.y
ANSWER: The original change assumed a standalone utility statement runs with no snapshot. A snapshot can still be held in some cases: an enclosing transaction at REPEATABLE READ or SERIALIZABLE (transaction snapshot), an already-registered or active snapshot, or a call via a portal or the extended protocol. The WAIT then sleeps with the snapshot pinned. The snapshot's xmin can conflict with replay (a recovery conflict or vacuum-cleanup conflict), so replay is blocked, the LSN is never reached, and the session deadlocks against startup. The fix probably pops or releases the snapshots, or rejects use inside a transaction that holds one. The property broken is that WAIT FOR must not hold a snapshot or block replay (no self-deadlock). I am less sure the follow-up concerned the timeout (ms parsing, overflow, or a zero or negative value); I cannot rule that out.
CONFIDENCE: low for (a); low for (b)
DRILL: Read WaitStmtUtility / ExecWaitStmt in commands/wait.c for snapshot handling, and its call site in tcop/utility.c (PlannedStmtRequiresSnapshot); check git log for wait.c.

## R4-03
FILES: backup/basebackup_incremental.c, backup/walsummary.c, postmaster/walsummarizer.c
ANSWER: The fix is in the code that merges the summaries for the backup's LSN range (PrepareForIncrementalBackup). A single BlockRefTable is built by replaying all summary files in strict LSN (timeline) order. Each summary's per-relation-fork records are applied in turn: modified blocks are marked, and the truncation "limit block" is applied as it arrives. A limit only discards block references from earlier summaries; blocks modified after the truncation in the same or later summaries are kept. The earlier bug was that a truncation limit was combined independently or out of order, so it also wiped later modifications. The driving constraint is that a limit block is a point-in-time event: it invalidates earlier references only, and later modifications must survive. Ordering therefore matters, and summaries must be merged chronologically.
CONFIDENCE: medium for (a); medium for (b)
DRILL: Read PrepareForIncrementalBackup in basebackup_incremental.c (the summary-reading loop, the BlockRefTableReader, and how limit_block is applied) together with blkreftable.c in src/common.

## R4-04
FILES: replication/walsender.c, storage/lmgr/condition_variable.c, access/transam/xlog.c, access/transam/xlogrecovery.c
ANSWER: A walsender that only calls ConditionVariablePrepareToSleep, and never sleeps on the CV or cancels, stays registered in the CV wait list. Broadcast removes every waiter from the list, so after one wakeup the walsender is no longer registered and misses later wakeups unless it re-registers each loop. Stale membership also leaves cv_sleep_target set. If the process then errors, exits, or switches to a different CV (e.g. logical vs physical senders, or after a timeline or promotion change), the stale entry causes lost wakeups or spurious latch sets. A proclist entry for a dead or reused PGPROC would corrupt the list. The fix is probably to cancel the sleep on error and exit, and to re-prepare on every wait. The properties broken are no lost wakeup (replication lag or a stalled walsender) and wait-list consistency.
CONFIDENCE: low for (a); low for (b)
DRILL: Read WalSndWait, WalSndWakeup, WalSndErrorCleanup and the wal_flush_cv / wal_replay_cv code in walsender.c, and ConditionVariablePrepareToSleep / CancelSleep / Broadcast in condition_variable.c.

## R4-05
FILES: commands/subscriptioncmds.c, replication/logical/worker.c, replication/logical/tablesync.c, replication/logical/launcher.c, replication/walsender.c
ANSWER: The original change did not handle every state or interleaving of the two_phase transition. A 2PC state-machine step was missing: the subscriber's PENDING to ENABLED change, the slot's two_phase flag (alter-slot on the publisher), and the apply or tablesync workers' restart can disagree. Examples are ALTER while tablesync is incomplete, REFRESH PUBLICATION adding tables, workers started before the slot flag is switched, or the alter running inside a transaction block (remote slot changes are non-transactional). The result is that a prepared transaction is either applied twice, as PREPARE plus COMMIT PREPARED with its changes replayed, or skipped. A "no pending prepared transactions" check that misses the in-flight case could produce the same result. The property broken is exactly-once, in-order apply of prepared and committed transactions across the subscriber and the slot.
CONFIDENCE: low for (a); low for (b)
DRILL: Read AlterSubscription (the two_phase branch) in subscriptioncmds.c and the two_phase state handling (AllTablesyncsReady, the pg_subscription.subtwophasestate update) in worker.c and tablesync.c.

## R4-06
FILES: replication/logical/reorderbuffer.c, replication/logical/decode.c, replication/logical/snapbuild.c, replication/logical/logical.c
ANSWER: The original change used the CLOG abort status at the time of the check to discard a transaction's changes. It overlooked cases where that status is not final or not safe for this transaction. A transaction may be prepared, or still in progress or streamed in part (changes already sent to the subscriber), or a crashed transaction with no explicit abort record. A subtransaction's abort status may differ from its parent's. Dropping changes without updating the rest of the txn state leaves the subscriber out of sync: it gets no stream abort or rollback, or the prepared or later changes are still decoded. The decoder state also becomes inconsistent: memory accounting, the txn's size counter, the base snapshot, and invalidations. The correctness property is that the output must still match the transaction's final outcome with consistent reorder-buffer state. The skipped transaction must be handled as aborted exactly once.
CONFIDENCE: low for (a); low for (b)
DRILL: Read the new abort-check call and ReorderBufferCheckMemoryLimit / ReorderBufferTruncateTXN / ReorderBufferResetTXN in reorderbuffer.c, and the TransactionIdDidAbort call site; then check git log for the follow-up.

## R4-07
FILES: optimizer/util/plancat.c, access/common/tupdesc.c, utils/cache/relcache.c, commands/tablecmds.c, executor/execTuples.c
ANSWER: attnotnull now only means a not-null constraint exists, valid or not. The cached per-column nullability state in the tuple descriptor (also used by deforming and JIT) is set from attnotnull or the constraint, so a NOT VALID constraint is treated as proving non-null. Rows violating it can exist while the constraint is invalid. This breaks when code uses attnotnull or the tupdesc's non-null state as proof of no NULLs: planner optimizations (IS NULL and IS NOT NULL qual removal, join and antijoin reduction, uniqueness), the executor's fixed-offset deforming fast path, and any place that copies nullability into a new or rebuilt descriptor, such as relcache build, CREATE TABLE AS, or inheritance. The result is wrong query results or wrong tuple deforming when NULLs exist. The property broken is that attnotnull and the nullability cache may only be treated as guaranteed non-null once the constraint is validated and enforced.
CONFIDENCE: low for (a); medium for (b)
DRILL: Grep for attnotnull / attnullability use in plancat.c (get_relation_info notnullattnums), tupdesc.c (TupleDescFinalize / populate_compact_attribute) and relcache.c RelationBuildTupleDesc, and check how the invalid state is filtered.

## R4-08
FILES: catalog/pg_shdepend.c, commands/user.c, catalog/aclchk.c, catalog/catalog.c, commands/dbcommands.c
ANSWER: Grants now carry a shared dependency on the grantor. The change overlooked cases where the dependency bookkeeping and the grant rows disagree. Grants made by the bootstrap superuser (pinned role) or self-referential grants, and revokes, role renames, and grants dropped via DROP ROLE of the member or role, may leave pg_shdepend entries dangling or missing. DROP OWNED BY and REASSIGN OWNED BY must treat pg_auth_members specially: DROP OWNED removes the grants, REASSIGN leaves them. The consequence is that DROP ROLE wrongly fails with "role cannot be dropped because some objects depend on it", or succeeds and leaves a dangling grantor. The property broken is referential integrity of the grantor in pg_auth_members, enforced via pg_shdepend, which also needs a correct OID assigned for each new row.
CONFIDENCE: low for (a); low for (b)
DRILL: Read how shdepDropOwned / shdepReassignOwned handle AuthMemRelationId and where user.c (AddRoleMems / DelRoleMems) records or deletes the shared dependency.

## R4-09
FILES: catalog/pg_publication.c, replication/pgoutput/pgoutput.c, commands/publicationcmds.c, commands/tablecmds.c, utils/cache/relcache.c
ANSWER: Exclusion is recorded only on the named root in pg_publication_rel (prexcept). The code that decides whether a table is published must apply that exclusion to every current and future partition. That includes publish_via_partition_root=false, where partitions are published under their own names, and partitions attached later. If a path (pg_get_publication_tables, GetAllTablesPublications, pgoutput's get_rel_sync_entry / ancestor lookup, or the publication-membership check in relcache) ignores the excluded flag or the ancestor, a partition of an excluded root is still replicated. A related miss is cleanup when an excluded table is dropped, detached, or has its schema changed, which leaves stale pg_publication_rel rows. The consequence is that data from an excluded table or partition leaks to subscribers. The property broken is that the publication filter must respect the exclusion.
CONFIDENCE: low for (a); low for (b)
DRILL: Read the pg_publication_rel prexcept handling in pg_publication.c (GetAllPublicationRelations, pg_get_publication_tables, is_publishable_relation / GetRelationPublications) and pgoutput's get_rel_sync_entry for the partition and ancestor path.
