CANDIDATE 1 (most likely)
FILE: src/backend/utils/time/snapmgr.c
FUNCTION: ExportSnapshot (and the matching sof/sxcnt parsing in ImportSnapshot)
DEFECT: Export treats suboverflowed the same on a standby as on a primary. If snapshot->suboverflowed (or subxcnt+nchildren exceeds the max) it writes "sof:1" and drops the whole subxip array. On a standby (takenDuringRecovery) subxip holds ALL running top-level and sub xids and xip is empty, and XidInMVCCSnapshot still searches subxip after the pg_subtrans lookup. ImportSnapshot only reads sxcnt/sxp when sof==0, so the importer ends up with subxcnt=0 and an empty xip.
FAILURE: Exporting on a hot standby while the KnownAssignedXids subxid cache has overflowed: the imported snapshot treats every in-progress transaction (xmin <= xid < xmax) as not running. Those transactions look committed or aborted, so uncommitted rows become visible and wrong hint bits can be set.
RULE: A snapshot built or imported outside GetSnapshotData must list every in-progress xid, and recovery snapshots keep all xids in subxip even when overflowed (I2.R3/R15).
CONFIDENCE: high

CANDIDATE 2
FILE: src/backend/utils/time/snapmgr.c
FUNCTION: ImportSnapshot
DEFECT: The importer does not take the recovery layout into account. When takenDuringRecovery is set, the xcnt/xip and subxip sanity checks and the sof handling follow the primary layout, so the snapshot's meaning is lost once the file is written.
FAILURE: A snapshot exported on a standby is imported with the wrong layout (see candidate 1).
RULE: Recovery-snapshot layout (all xids in subxip, xip empty) must survive the export/import round trip.
CONFIDENCE: low
