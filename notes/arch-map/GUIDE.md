## 0. 目的与非目标

目的：

1. 让人和模型先在抽象层面确认意图、定位改动，再按需下钻到代码。两类读者要的东西不同（v0.7，依据见 P.4 第 3 项）：
   - **人**：不读代码，也能理解架构为什么长成这样，并能推出改动的后果。主要产物是 `derivation.md`。
   - **模型**：它对 PostgreSQL 的先验很强，地图里的知识九成以上它本来就知道；给它的只是它不知道的那一小部分（`model-delta.md`），
     其余内容作为带证据锚点的底稿，供需要时查证。
2. 让地图暴露"抽象没做好"的地方，并能据此判断哪些值得改、哪些不值得改。
3. 把 PostgreSQL 社区在提交信息和邮件讨论中做过的取舍沉淀成原则，
   让后续的改进方向能从图上直接读出来。

非目标：

- 不追求完整的文档。模型本来就能读懂、也很少出问题的部分，只写一行。
- 地图不是权威。权威顺序仍然按 AGENTS.md：代码 > 测试 > README >
  官方文档 > 带 `Discussion:` 的提交 > 未结的讨论。地图只是带证据锚点的索引。
- 不编造 rationale。凡是不能指到提交或邮件的结论，一律标记为"假设"。

## P. 阶段划分与第一阶段的定义

| 阶段 | 目标 | 本文相关章节 |
|---|---|---|
| **第一阶段：骨架** | 搭起 PG core 的整体架构和抽象框架，讲清本质：每块负责什么、维持什么不变量、为什么这样设计 | §1–§3、§4.1–§4.2、§7–§9 |
| 第二阶段：下钻 | 对第一阶段暴露出的热区做 L2+ 建模，系统收集和分类残差 | §5 |
| 第三阶段：改进 | 基于原则和残差提出接口清洁化方向 | §4.3、§6 |

第二、三阶段只有在第一阶段验收通过之后才开始。

### P.1 第一阶段的目标

做出一张**覆盖完整、内容正确、体量足够小**的 PG core 本质地图。读完这张地图
（不读代码），人或模型应当能回答三类问题：

1. **是什么**：某个功能或某个改动落在哪个子系统、哪个 L1 模块，它会用到谁。
2. **守什么**：这块代码必须维持哪些不变量，这些不变量在并发和失败下如何成立，
   改动会把哪些不变量置于风险之中。
3. **为什么**：这块为什么设计成现在这样，基础性的取舍是什么，依据是哪个提交或哪次讨论。

### P.2 第一阶段的产出

| 产出 | 内容 |
|---|---|
| `L0.md` | 总图。推导链的根：力、根层决策、每个不变量族由哪些决策推出、每条决策的下游。12 个子系统，每个写：L1 模块清单、Owned state、1–3 条关键不变量、Depends、Derives from。另有不变量强制点矩阵和文件归属规则 |
| `subsystems/<n>.md` | 每个子系统列出 L1 模块，每个模块一行：Secret 加上它对应的源码目录或文件。**只有拥有 I1–I8 相关状态、并且是该不变量强制点的模块才写完整卡片**。本子系统的决策也记在这里（一行式，§4.2） |
| `invariants/I1..I8.md` | §8 的模板全部填完：不变量、跨度、在哪里被强制、并发与失败语义、校验手段、为什么这样设计 |
| `principles.md` | 推导链的根（§1.4）。按 §4.5 的规范写：环境前提 E、力 F、取舍规则、基础性决策（完整记录）、原则 R。它的作用是推导、裁决、重审，必须满足完备、独立、一致、可判定、有前提、有据可证伪 |
| `residuals.md` | 只**记录**建模过程中顺手发现的残差（不变量跨度大、职责过重、孤儿、地图和代码对不上），**不分析、不提方案**，每条一行 |
| `derivation.md` | 给人读的推导主线：从力和环境前提出发，按因果顺序讲每条基础性决策（要解决的问题、选择、另一条路、于是必须有、代价、来历、自测题），再讲决策之间的交叉、取舍规则和正在松动的前提。内容全部来自上面各文件，不引入新事实；地图更新后要同步 |
| `model-delta.md` | 给模型的增量：把 `invariants/` 的规则逐条出题，让几档模型不看材料作答，只收它们都答不出的要点（`tests/prior/`） |

上面前五项是底稿，后两项是从底稿生成的、分别面向人和模型的读物。

**体量不设数字上限。** 优先级是：先达到目的（用地图能做出正确的推理和决策，§1.1），再求简洁。
按 §1.2，错误代价远大于阅读成本，所以不能为了省篇幅而删掉回答问题所必需的内容，尤其是不变量、适用条件和失败语义。
在达到目的的前提下，每一行都应当必要，表述尽量简洁。

- 一行是否该写、怎么写，用 §3.1 的取舍标准判断：三个检验（必要、不可推导、代码里拿不到），加上四条简洁规则。
- 整体是否过大，用 §2.4 的分层曲线判断：每加一层带来多少准确率提升。不用预先定下的行数或 token 数判断。
- 地图按层组织，读者只读到够回答问题的那一层：L0 → 子系统的 L1 表 → 模块卡 → 代码。
  上层不重复下层的细节，下层不与上层矛盾（§1.3）。

### P.3 第一阶段不做什么

- 不做优化建议，不做"值不值得改"的判断，不提重构方案。
- 不下钻到 L2 及更深的层次。
- 不开发自动化工具。需要的数据用 §9 里的 git 命令手工获取（验收用的一次性检查脚本不算）。
- Tier S 的模块只占 L1 表一行，不写卡片。Tier 按模块定：Tier S 的子系统里也可以有需要写卡的强制点模块
  （例如运行时基础设施里的内存上下文、错误处理、ResourceOwner）。

## 1. 第一性原理

### 1.1 抽象的目的

光能复述描述不算理解。**理解一个系统 = 能正确预测干预的后果**：改了 X 会发生什么，
会破坏什么，为什么不能那样做。"深刻"指的是对**没见过的新干预**也能推对。

抽象的目的：**用尽量少的信息，对系统做出正确的推理和决策。**
抽象的好坏总是相对于一组问题而言；对 PG，这组问题取自开发者真实做过的改动和讨论
（git 历史、邮件列表）。

### 1.2 唯一的目标量：期望总成本

```
期望总成本 = E[任务] ( 阅读成本(地图 + 下钻) + Σ 错误代价 × 出错概率 )
```

- 错误代价不对称：漏掉一个不变量风险（数据损坏、结果错误）远比定位偏一个文件严重。
  所以不变量和失败语义值得分配最多的篇幅。
- 其余所有指标（§2.3）都只是用来解释这个量为什么高。

### 1.3 好抽象的形式条件：交换性

```
具体状态 ──具体操作──▶ 具体状态'
    │抽象                │抽象
    ▼                   ▼
抽象状态 ──抽象操作──▶ 抽象状态'
```

- 程序语言理论把抽象形式化为**抽象函数 + 表示不变量**（Hoare 1972；Liskov & Guttag）：
  上图可交换，抽象才正确。不变量本来就是抽象定义的一部分，这是"不变量是核心"的根据。
- 因果抽象（Rubenstein 等 2017；Beckers & Halpern 2019）：高层干预与底层干预结果一致。
- **层与层之间也要满足**：下层只能细化上层，不能与上层矛盾；上层能回答的问题不必看下层。
- 泄漏不可避免，**但必须标注**：每条抽象写明适用条件（持有什么锁、是否在恢复中……），
  条件之外写"取决于细节，见 `[[ID]]`"。没标注的泄漏是最危险的情况。

### 1.4 最短的描述是生成式的

设计出来的系统，其结构是由少数"力"（必须满足的约束）和"决策"（对力的取舍）推出来的。
因此最短、也最能推广的描述，不是平铺的模块清单，而是一条推导链：

```
力（目标） × 环境前提（世界） → 决策 → 不变量 → 模块 → 代码
```

每一层都应当能由上一层加上少数选择推出来。这样组织有三个直接好处：

1. **新干预可以推导**：知道力和决策，就能推出某个新改动会撞上哪些不变量。
2. **原因直接在图上**：每个模块、每条不变量都能回答"为什么存在"。没有上游的节点
   就是孤儿，它本身就是一种残差。
3. **改进方向自然出现**，有三种来源：
   - **力变了**：硬件、负载、部署环境变化后，沿推导链重推一遍，看哪些决策已经不再最优；
   - **原始原因失效**：一个决策当初的理由已不成立，而现在维持它的理由可能不同；
   - **代价集中**：一个决策的下游代价（bug 热区、到处的特例）都挂在它下面，一眼可见。

PG 的例子（需要在 `principles.md` 中补齐证据）：

- **不覆盖写的存储**。时间旅行查询于 1997 年移除（`32cd09ac6d4` "Good Bye, Time Travel!"），
  WAL 代码 1999 年才出现（`30659d43eb7`）。这两个提交的信息都只有标题级内容，只能证明时间点，
  不能证明"原始动机是时间旅行"；这一句在找到 Stonebraker 1987 的原文之前按假设对待（§12）。
  现在维持它的理由是 MVCC 读写不互相阻塞（官方文档）。它的下游已由地图算出：`D-mvcc-no-overwrite`
  下挂的模块卡最多，包括 pruning 与 HOT、vacuum 与 freeze、visibility map、xid 空间、快照、
  standby 冲突（L0 §2.3）。multixact 不在其中：它的上游是"行锁记在元组头"，这条决策目前还缺。
- **每连接一个进程**：多核和大量连接改变了这里的力，于是有了多线程化的讨论
  （假设，链接待补）。
- **依赖 OS page cache**：存储硬件变化改变了这里的力，于是有了 read stream
  （`b5a9b18cd0b`）和 AIO（`io_method`）。

**防止事后合理化**：推导链上的每条边都要有证据。每个决策要区分三种原因：
**原始原因、当前原因、假设**。历史偶然（路径依赖）就如实写成偶然，不要硬编一个理由。

### 1.5 由此推出的三条工作原则

1. **导航靠压缩，诊断靠残差。** 地图与代码、历史、原则对不上的地方，就是需要下钻、
   或可能需要重构的地方。
2. **分清本质复杂和表示复杂。** 不变量在上一层能一句话说清、实现却到处散落，属于表示问题；
   不变量本身就说不清，属于本质复杂，写进协议视图并补校验手段（§6 模式 G）。
3. **深度按期望成本分配**（§3）。地图的篇幅只花在错误代价高、或现在做不好的地方。

## 2. 最小建模单元：模块卡

### 2.1 卡片字段（共 7 个，不要再加）

| 字段 | 回答什么问题 | 依据 |
|---|---|---|
| **Secret** | 这个模块隐藏了哪个可能变化的设计决策 | Parnas 1972 |
| **Owned state** | 它独占哪些状态，谁可以写，在哪个进程或内存里 | 单写者原则 |
| **Invariants** | 关于这些状态，什么必须永远成立（一句话一条） | 本指南核心 |
| **Contract** | 对外承诺什么，包括**适用条件**、并发语义（需要什么锁）和失败语义（error / crash / cancel / standby 下会怎样） | DB 的特殊性；§1.3 |
| **Depends** | 它使用了谁（Parnas 的 "uses" 关系，不是目录包含关系） | Parnas 1979 |
| **Derives from** | 它由哪个决策推出（`[[D-xxx]]`；追不到决策时才直接写力 `[[F<n>]]`）。判据：去掉这条决策，这个模块或它的核心不变量就不必存在，或会是另一个样子。推不出来就写"孤儿"并记为残差；只有部分内容能追到的，写明缺口 | §1.4 |
| **Evidence** | 文件、README 章节、测试、提交 hash、Discussion 链接 | 可证伪 |

另外附两个状态标签：**Tier**（S/B/A，见 §3）和 **判定**
（优化 / 保持 / 不值得，见 §4.3）。

### 2.2 为什么不变量是核心，但不是全部

不变量定义了一个模块"正确"的含义。但对数据库内核来说，只有不变量还不够，
还需要三样东西：

- **谁拥有状态**：不变量约束的是某一份状态，必须先明确这份状态归谁。
- **在并发下是否成立**：不变量在什么锁、什么可见性条件下成立。
- **在失败时是否成立**：error、崩溃、取消、主备切换之后，不变量还成不成立。

PG 里大部分严重 bug，都不是不变量本身写错了，而是在并发或失败路径上被破坏了。
所以卡片的骨架是：**状态 → 不变量 → 并发与失败下的契约**。

### 2.3 指标：三个主量 + 六个诊断量

**主量**（直接构成 §1.2 的期望总成本，通过 §2.4 的测试测得）：

| 主量 | 问题 |
|---|---|
| **Q 充分性** | 只用地图，对干预的预测有多准（按错误代价加权） |
| **S 体量** | 地图占多少 token。先保证 Q 和 C 达到目的，在此前提下越小越好；不设门槛，按层分别报告 |
| **C 自知性** | 答错的地方，是否给出低置信，并指出该往哪里下钻 |

**诊断量**（只用来解释主量为什么差，本身不是目标）：

| 诊断量 | 定义 | 典型解释 |
|---|---|---|
| **D1 不变量跨度** | 维持一条不变量需要多少模块协作 | 跨度大 → 风险题答不对 |
| **D2 写者数** | 一份共享状态有几个写者 | 多写者 → 并发题答不对 |
| **D3 失败语义覆盖** | error / crash / cancel / standby 是否都有定义 | 有空缺 → 失败路径题答不对 |
| **D4 变更局部性** | 历史提交在这一层落在几个节点（git 共变） | 经常跨节点 → 落点题答不对 |
| **D5 接口深度** | 接口大小相对隐藏的功能 | 浅接口 → 体量大，信息却少 |
| **D6 推导完整性** | 节点能否追溯到决策和力；孤儿有多少 | 孤儿多 → 原因题和推导题答不对 |

初步观察（假设，待用 D1 正式验证）：最近 7 年 bugfix 密度最高的子系统
（§7 表）恰好是不变量跨进程、跨崩溃的那些，即 replication、WAL、process/ipc。

### 2.4 主量的测法

1. **出题**：用真实的历史干预。只给提交的意图（标题、问题描述），不给 diff。
2. **五类问题**，都有客观答案；初始权重按错误代价设定，第一轮跑完再校准：

   | 题型 | 问什么 | 答案来源 | 初始权重 |
   |---|---|---|---|
   | 落点 | 会改哪些模块 | 实际 diff | 1 |
   | 风险 | 会危及哪些不变量、可能破坏什么 | 后续"Fix … from commit X"一类的修复提交 | 3 |
   | 原因 | 为什么这样设计 | 提交原文、邮件讨论 | 2 |
   | 反事实 | 为什么不用某个替代方案 | 邮件中被否决的方案和否决理由 | 2 |
   | 推导 | 给定力和决策，推出后果（例如：不覆盖写会带来哪些必要的维护机制） | 代码与历史 | 2 |

3. **三组对照**：

   | 条件 | 用来排除什么 |
   |---|---|
   | 不给地图 | 模型对 PG 的先验知识 |
   | 给同样 token 数的 README 原文 | "只是多给了信息" |
   | 给地图 | — |

   只有地图明显好于第二组，才说明压缩有效。

   以上三组是闭卷，量的是地图本身含有多少读者没有的信息。地图的用途是"先读地图，再按需下钻"（§0），
   所以主比较是**开卷**的两组：都给修复前的代码快照（不带 git 历史），限定工具调用次数，一组带地图，一组不带；
   比较风险题得分和耗用的 token。
4. **分层曲线**：分别只给 L0、L0+L1、……，看每加一层的**每 token 准确率提升**，
   以及模型是否在该下钻的时候下钻。
5. **自知性**：每个回答附置信度。答错且高置信的条目，就是没标注的泄漏，
   要么修地图，要么记成残差。
6. **新题**：补充一些没发生过的改动意图，防止模型靠记忆答题；由熟悉 PG 的人或邮件讨论评分。
7. **留出**：出题只用地图没有引用过的提交。每轮先划定一个留出的时间窗口，建图和写 `invariants/` 时不得引用窗口内的提交
   （已经出过题的除外）。窗口、题库、答卷和结果放在 `tests/round<n>/`；用过的题只能当回归集。

## 3. 复杂度控制：三档深度

| Tier | 何时使用 | 产物 |
|---|---|---|
| **S** | 稳定、bug 多为局部、改动局部，或代码是外部引入的 | L1 表里一行就够 |
| **B** | 有一定痛点，但不变量跨度小 | 一张模块卡 |
| **A** | 有证据表明是痛点：bugfix 密度高、跨度大、社区反复讨论 | 模块卡 + 协议视图 + 决策记录 + 残差 |

Tier 按模块定，不按子系统定；§7 表里的 Tier 是该子系统多数模块所在的档。

### 3.1 取舍标准（由建图的 agent 自己判断，不设数字上限）

依据只有一条：§1.2 的期望总成本。**一条内容值得写，当且仅当删掉它会让期望总成本上升。**
落到操作上，是下面三个检验，三个都通过才写：

| 检验 | 问自己 | 不通过的典型内容 |
|---|---|---|
| **必要**：去掉它，有题答不好 | 去掉它，§2.4 的哪一类题（落点、风险、原因、反事实、推导）会答错，或者必须付出昂贵的下钻？说不出具体的题就不写 | "这个模块很重要"之类的评价；完整的函数清单 |
| **不可推导**：地图里别处推不出来 | 能否由上游的力、决策、不变量，加上一句常识推出来？能推出就只写源头，不写结果 | 把同一条不变量在每个模块里各抄一遍 |
| **代码里拿不到**：从代码或 README 无法便宜、可靠地拿到 | grep 一下、读一个文件就能可靠得到吗？能，就只留一个指针（`file:` / `readme:`） | 文件列表、结构体字段、参数含义 |

反过来，以下几类内容**通常都能通过检验，应当写**，因为代码里看不出来，而且错了代价很高：
跨模块的不变量；适用条件和失败语义；决策的原因、被否决的方案和代价；
"看起来可以这样做，但不行"的陷阱；指向下一层的下钻指针。

写的时候遵守四条简洁规则：

1. **写在它成立的最高一层。** 由哪个决策推出，就写在那个决策下面；下层只引用 `[[ID]]`，不复述。
2. **一事一处。** 同一个事实只有一个出处，别处一律用引用。
3. **一句话能说清的不写一段。** 写不成一句话，先想想是不是抽象还没找准（这本身可能就是残差）。
4. **证据用指针，不贴原文。** 写 `commit:<hash>`、`file:<path>:<line>`，不摘抄大段代码或邮件。

**删减方向的检验**：第一轮 §2.4 测试之后，答题从来没用到、也删掉后不影响答题的内容，删掉或下沉一层；
答错或靠大量下钻才答对的地方，补内容或补下钻指针。体量大小只是这样调出来的结果，不是预先定的目标。

**降级规则**：Tier A 节点如果连续两轮主量测试（§2.4）都没产生有用信息，就降到 B。

## 4. 原则与价值判断：从提交和邮件中提取

### 4.1 证据来源（按优先级）

1. 提交信息正文，特别是 `Discussion:` 链接、"we used to … because …"
   这类写法，以及作者写明接受的代价。
2. `pgsql-hackers` 讨论串：设计取舍，以及**被否决的方案和否决理由**。
3. `pgsql-bugs` 和 bugfix 提交：痛点在哪里。
4. README、代码注释中的 "We do X because Y"。
5. PG wiki 的 Not Worth Doing（其中有 "Features We Do Not Want" 一节）和 OptimizerHintsDiscussion 等页面，链接见 §11。

### 4.2 决策记录

两种形式，同一个 ID。

**一行式**：每条决策都有，记在所属子系统文件的"设计原因（决策）"小节。

```
- D-<slug> {[[F1]] [[F4]]} <一句话决策> ← 原始: <原因>〔证据〕；当前: <原因>〔证据〕；假设: <推断>
```

**完整记录**：只给基础性决策写，记在 `principles.md`。

```
D-<slug>  <一句话决策>
力:         [[F..]]
原始原因:   做出决策时的理由
当前原因:   基线代码今天给出的理由
被否方案:   <方案> — <否决理由>（来自讨论串；没有证据就不写）
推出:       由它推出的不变量族和模块（[[I..]] [[S..M..]]）
下游代价:   <代价> → <补偿手段>
重新审视的条件: <什么情况下应该重新考虑>
证据:       commit:<hash>; url:<Discussion 链接>
```

原因分三种，不能混写（§1.4）：

- **原始**：依据必须是引入它的提交信息、当时的文档或论文。查不到就写"未考证"，不要把现行理由当成原始理由。
- **当前**：依据是现行 README、代码注释、官方文档。
- **假设**：没有锚点直接支持的推断。

力到决策的归类是建图者的判断，在 `principles.md` 给出逐条证据之前按假设对待。

示例（取自提交原文）：

```
D-idx-am  index AM 能力从 pg_am 的列改为 C 层 handler 结构体
力:         [[F3]] [[F1]]
原始原因:   函数签名无法被编译器检查；扩展难以定义新的 AM
下游代价:   SQL 层的 opr_sanity 交叉检查失效 → 补偿手段是 amvalidate
证据:       commit:65c5fcd353a
```

### 4.3 价值判断（第三阶段才用，这里只记原因）

第一阶段不做"值不值得改"的判断，只把**原因**记进决策记录。
一个设计之所以值得改或不值得改，归根到底取决于以下几类原因，第三阶段再系统使用：

- 痛点证据：bug 多、经常需要多处一起改、社区反复抱怨；
- 是否存在已知的更好做法：PG 自己的先例，或其他系统的先例；
- 社区态度：以前是否否决过同类提案，兼容性代价能否接受；
- 本身是否稳定：bug 是否都是局部的，代码是否是外部引入的（regex、snowball）。

### 4.4 原则的成立条件

- **候选原则**：只有一条决策支撑。
- **确认原则**：有两条或更多独立决策支撑，且没有找到反例。

当前候选（每条都需要更多决策来支撑）：

| 原则 | 支撑决策 |
|---|---|
| R1 数据表示必须让 `equal()` 可信，即相等就代表同一个值 | `2489d76c490` |
| R2 扩展点使用 C 层 handler 结构体，catalog 里只存名字和 handler | `65c5fcd353a` `8586bf7ed88` `5c279a6d350` `b8bff07daa8` |
| R3 用统一机制取代特例逻辑 | `3fc6e2d7f5b` `86dc90056df` `b8d7f053c5c` |
| R4 持久化格式自描述，好让外部工具通用实现 | `2c03216d831` |
| R5 兼容性代价必须显式写出 | `2489d76c490`（FDW 必须跟着改） |

**原则残差**：某个节点违背了一条确认原则 → 自动成为候选改进点（§5）。

### 4.5 `principles.md` 规范

#### 4.5.1 根本作用

`principles.md` 是推导链的根（§1.4）。地图其余部分回答"是什么、守什么"；这个文件回答**"为什么必然如此，以及换个条件会怎样"**。
它的作用只有三项，下面所有要求都由它们反推出来：

| 作用 | 读者凭它能做到什么 | 对应的检验（4.5.6） |
|---|---|---|
| **推导** | 只看这份文件，就能推出 PG 必须具备哪些机制、哪些不变量族，以及原因 | 重构检验 |
| **裁决** | 遇到一个新的设计问题，能预测社区会选哪个方案、否决哪个、理由是什么 | 裁决检验 |
| **重审** | 当环境前提变化时（硬件、负载、生态），能指出哪些决策需要重新审视 | 敏感性检验 |

做不到这三件事的内容，不管写得多漂亮，都不属于这份文件。

#### 4.5.2 由作用反推的六条质量要求

把这份文件看成一个"公理系统"：用少量前提，推出整个架构。好的公理系统有以下几个性质：

1. **完备**：每个不变量族（I1–I8）和每个子系统，都能沿着 力/前提 → 决策 的链追溯上来。
   追溯不到的是孤儿，记进 `residuals.md`（这是推导作用的要求）。
2. **独立（最小）**：一条基础性决策如果能由其他决策加上力推出来，它就不是根，应当降为派生，
   写在推出它的那个子系统里（这是简约的要求，§3.1 的"不可推导"）。
3. **一致**：两条原则在某个情形下给出相反结论时，必须有一条取舍规则说明这种情况下谁优先。
   否则裁决作用无法成立。
4. **可判定**：每个力、每条原则，都要写到能对一个具体问题给出裁决的程度。
   "性能很重要"这种口号什么也裁决不了，不合格（这是裁决作用的要求）。
5. **有前提**：每条决策都显式列出它依赖的环境前提。
   一个决策该不该重审，取决于它的前提是否已经变了（这是重审作用的要求）。
6. **有据、可证伪**：原因分原始、当前、假设三种，各自配证据（§4.2）。
   每条原则要列出它能预测的决策，以及已知的反例。一条原则如果什么都预测不了，就不是原则。

#### 4.5.3 构成要素与文件结构

按推导顺序排列，前一部分是后一部分的输入：

```
1. 环境前提 E<n>     系统所处的世界：OS、硬件、负载、生态
2. 力       F<n>     系统必须达到的目标
3. 取舍规则          力与力冲突时，谁优先、在什么条件下
4. 基础性决策 D-*    由 力 × 前提 × 取舍规则 推出的根层选择
5. 原则     R<n>     从多条决策中归纳出来、可以用来裁决未来问题的规律
```

**为什么前提要和力分开**：力是"想要什么"，基本不变；前提是"世界是什么样"，会变。
把二者混在一起，就无法回答"哪些决策因为世界变了而需要重审"。
例如 [[D-own-buffer-cache]]、[[D-process-per-connection]] 的理由里，有相当一部分是对 OS 和硬件的假设，而不是目标本身。

#### 4.5.4 各要素的写法

**环境前提 E**：只收被至少一条基础性决策依赖的前提。

```
E<n>  <一句话陈述世界的某个事实>
依赖它的决策: [[D-..]]
现状: 仍成立 / 正在变化（证据） / 已失效（证据）
证据: ...
```

**力 F**：一个力合格的条件是：至少有一条基础性决策为它而做，并且它至少在一条决策中被拿来与别的力交换过。
从不参与取舍的约束，归为前提或不变量，不算力。

```
F<n>  <名称>
要求: 可判定的陈述（违反它的具体表现是什么）
在 PG 中的约束点: 它主要约束哪些子系统和不变量族
证据: 社区或文档明确表述这一目标的出处
```

**取舍规则**：只能从决策记录的"下游代价"字段归纳得来，因为那里写明了牺牲了哪个力、换来了哪个力。不允许凭印象排序。
它不一定是全序：有的力几乎从不让步，有的取舍取决于条件。

```
Fa vs Fb: <在什么条件下，优先谁>；<让步的一方怎样补偿>
支撑: [[D-..]] [[D-..]]   反例: [[D-..]] 或 "未见"
```

**基础性决策 D**：沿用 §4.2 的完整记录格式，再加一个字段 `前提: [[E..]]`。
满足下面**任一**条，就是基础性决策，写进本文件；否则只在子系统文件里写一行（§4.2）：

- 它推出了至少一个不变量族；
- 它的影响跨越两个或更多子系统；
- 推翻它，就要重推地图上大量节点。

在此之上还要通过独立性检查（4.5.2 第 2 条）。
子系统里的一行式决策，如果后来发现满足上述条件，就升级到本文件；ID 不变。

**原则 R**：原则不是"又一条决策"，而是**能复用到未来选择上的规律**。

```
R<n>  <祈使句式的陈述，能直接用来裁决>
适用范围: 什么情形下适用
解决的冲突: Fa vs Fb
支撑决策: [[D-..]] × ≥2（候选只需 1 条）
预测: 它会对哪类新问题给出什么裁决
例外/反例: ...
来源: 社区明言（附 url） / 由决策归纳
状态: 候选 / 确认（§4.4）
```

"社区明言"的证据强度高于"由决策归纳"。二者结论冲突时，以前者为准，并把这个冲突记为残差。

#### 4.5.5 生成方法

1. **自下而上收集候选**：来源包括各子系统文件里的一行式决策；重构类和正文较长的提交；
   README 中 "because" 一类的说明；POSTGRES 原始论文（用于追查原始原因）。
2. **按扇出筛选**：用 4.5.4 的三条标准，把基础性决策挑出来。
3. **独立性检查**：对每一条，尝试用其余决策加力推出它；推得出的就降级。
4. **反推力与取舍**：逐条读决策的"下游代价"，记下"牺牲了 Fx、换来了 Fy"，归纳成取舍规则。
5. **归纳原则**：寻找两条或更多决策共有的规律，**并且主动去找反例**：
   用 `git log --grep` 和邮件档案检索与该原则相反的决策。
6. **补前提**：对每条基础性决策问一句"世界的哪个事实变了，这个决策就不再成立？"，答案就是它的前提。
7. **留出检验集**：用来归纳原则的决策和讨论，不能再用来做裁决检验（4.5.6），否则就是循环论证。
   做法是先随机留出约四分之一的讨论和决策，归纳完成后再拿来检验。

#### 4.5.6 验收

**结构检查**（机械检查）：

- 完备：每个 I 族和每个 S 子系统，在本文件里都有 `推出` 指向它；
- 独立：每条基础性决策都满足扇出标准，并且记录了独立性检查的结论；
- 一致：凡是在同一情形下可能冲突的原则，都有对应的取舍规则；
- 可证伪：每条确认原则都写了"预测"，并且有不少于 2 条支撑决策。

**作用检验**（作为 §2.4 测试的一部分，只给模型看本文件和 `L0.md`）：

| 检验 | 做法 | 通过的标志 |
|---|---|---|
| 重构 | 让模型列出 PG 必须具备的机制和不变量族，并说明理由 | 与 L0 和 I1–I8 基本吻合，理由与决策记录一致 |
| 裁决 | 用留出的 hackers 设计讨论出题，让模型预测结果和理由 | 预测与实际结论一致；不一致的条目写进残差 |
| 敏感性 | 给出一个历史上真实发生过的前提变化（例如去掉时间旅行、AIO 的出现），问应当重审哪些决策 | 与历史上实际被重审的决策吻合 |

#### 4.5.7 常见错误

- 写成口号：力和原则无法裁决任何具体问题。
- 平铺所有决策：把局部决策也写进来，失去"根"的意义（违反独立和最小）。
- 一决策一原则：原则没有起到压缩作用。
- 事后合理化：用当前理由冒充原始理由，或者给历史偶然硬编一个理由。
- 循环检验：用归纳原则时用过的材料来验证这些原则。

## 5. 残差：五类，以及怎么分类

| 类型 | 怎么得到 |
|---|---|
| 依赖残差 | 地图上的 Depends 和 `#include`、调用关系对不上 |
| 共变残差 | git 历史里经常一起改，地图上却分属不同节点 |
| 预测残差 | §2.4 测试中答错、或答错却高置信的地方 |
| 原则残差 | 节点违背确认原则 |
| 交互残差 | 两个节点之间存在强耦合且跨层（见 §6 的 connascence 等级） |

每条残差必须归入以下三类之一，**只有第 3 类进入重构候选**：

1. 地图错了 → 修地图。
2. 本质复杂 → 写进协议视图，补校验手段（模式 G）。
3. 表示问题 → 套用 §6 的模式，再按 §4.3 判断值不值得做。

## 6. 接口清洁化模式目录

### 6.1 交互强度怎么衡量

用 connascence 等级，从弱到强：名字 / 类型 < 位置 < 含义 < 算法 < 执行顺序 / 时序。

交互复杂度 = 强度 × 距离（跨了几层）× 涉及点数。

让接口变干净，就是**把强耦合降级成弱耦合，或者把强耦合收进同一个模块**。

### 6.2 模式表

每个模式都包括：事前信号 → 变换 → PG 先例 → 外部先例 → 需要检查的代价。

| 模式 | 事前信号 | 变换 | PG 先例 | 外部先例 | 需要检查的代价 |
|---|---|---|---|---|---|
| **A. handler 结构体** | N 个实现 × M 个调用点直接耦合；扩展需求被卡住 | 抽出 ops 表，并把能力标志显式化 | `65c5fcd353a` `8586bf7ed88` `5c279a6d350` `b8bff07daa8` | Linux VFS ops；SQLite VFS；MySQL handler API（反面教训：如果接口只取各实现的公共部分、又不暴露能力，优化器就看不到各实现的特长） | 间接调用开销；ABI 稳定性 |
| **B. 把上下文写进数据表示** | 值相等但含义不同；同一个值的含义依赖它出现的位置 | 给值加上上下文标记 | `2489d76c490` `2c03216d831` `1a0586de365` | ARIES 的 pageLSN；Cascades 的 required/delivered 物理属性（PG 的 pathkeys 与之类似）；Galindo-Legaria & Rosenthal 关于 outer join 重排的工作 | 数据结构变大；第三方代码要跟着改 |
| **C. 并入统一框架** | 通用框架旁边长出面条式的特例逻辑 | 让特例也走同一个框架 | `3fc6e2d7f5b` `86dc90056df` `b8d7f053c5c` | Volcano/Cascades 统一的搜索框架；exchange 算子（PG 的 Gather 对应它） | 规划时间；短期内可能出现行为回归 |
| **D. 用代码生成消除重复** | 加一个东西要同步改 N 个文件 | 写一个生成器 | `964d01ae90c`（节点支持函数）、`372728b0d49`（catalog 初始数据改为 .dat，由 genbki 生成） | Coccinelle 对 collateral evolution 的研究；schema 驱动的代码生成 | 构建复杂度 |
| **E. 边界上错误当值返回** | longjmp 式的错误模型不适合某些边界 | 提供"软错误"通道 | `1939d26282b` 系列 | end-to-end argument（Saltzer 等） | 两套错误路径并存 |
| **F. 机制与策略分离** | 一个大文件同时承担多种职责 | 拆出机制层 | `aafc05de1bf` `98a64d0bd71` `b5a9b18cd0b` `5891c7a8ed8` `13df76a537c` | Levin 等《Policy/Mechanism Separation in Hydra》（SOSP 1975）；Lampson《Hints for Computer System Design》 | 增加一层间接 |
| **G. 不变量校验器**（专门对付本质复杂） | 不变量跨度大、无法再降 | 加一个运行时或离线校验器 | wal_consistency_checking、amcheck、pg_visibility、debug_discard_caches | Engler《Bugs as Deviant Behavior》；Linux lockdep（PG 目前没有对应的检查器，见 §12） | 运行开销（通常只在测试中开启） |

**使用顺序**：先判断复杂是本质的还是表示的（§1.3）。表示问题从 A–F 里选；
本质复杂用 G。

## 7. L0 地图：PostgreSQL core 的 12 个子系统

**文件归属按 Secret，不按目录。** 目录只是默认值；一个文件隐藏的设计决策属于哪个子系统，它就归哪个子系统。
例如 `postmaster/checkpointer.c` 归 WAL 与恢复，`storage/lmgr/lwlock.c` 归进程与 IPC，`storage/ipc/sinvaladt.c`
归 catalog 与缓存，`commands/vacuum.c` 归访问方法。这样划分后，一个改动意图落在哪里更容易预测（落点题），
一条不变量的强制点也更集中。完整的归属规则和例外清单以 `L0.md` §7 为准；下表只列主要目录。

数据口径：自 2019-01-01 起，提交信息匹配 `^fix|crash|race|corrupt`（忽略大小写）的提交数，

## 8. 横切不变量族（协议视图）

每个不变量族建一个文件，结构如下：

```
一句话不变量 / 跨越哪些子系统(D1) / 在哪些点被强制保证 / 校验手段
历史 bug 类别(带提交) / 后来的抽象改进(带提交) / 外部参照 / 当前残差
```

"强制点所在的子系统"一栏是第一轮建图实测的（有模块卡、且标了该族的模块所在的子系统）；
具体到模块的矩阵，以及每族由哪些决策推出，以 `L0.md` §6 为准。

| 族 | 一句话不变量 | 强制点所在的子系统（实测） | 现有依据或校验 | 外部参照 |

## 9. 工作流程（每个子系统都按这个走）

1. **骨架**：用 README、目录结构、`#include` 关系起草 L1 层和模块卡。
   Tier S 的部分到这里就结束。
2. **证据收集**（Tier B 和 A）：

   ```sh
   # 子系统的修复密度（复现 §7 表；在 bash 中执行）
   git log --since=2019-01-01 --format=%h -i \
     --grep='^fix\|crash\|race\|corrupt' -- <paths> | sort -u | wc -l
   # 带讨论链接的设计提交
   git log --format='%h %ad %s' --date=short -i \
     --grep='Discussion:' -- <paths> | head -200
   # 共变：哪些文件经常一起改
   git log --since=2019-01-01 --name-only --format='@@' -- <paths>
   ```

   重点挑三类提交：重构类（Restructure、Refactor、Introduce、Rework、Make … more）、
   修复中带 "because" 的、以及正文较长的提交。顺着 `Discussion:` 链接去读邮件。
3. **写卡**：填 7 个字段，并标出 D1–D3、D6。
4. **决策**：给重要的设计选择写决策记录；满足扇出标准的升级为基础性决策，按 §4.5 写进 `principles.md`。
5. **残差**：收集五类残差并分类（§5）；对第 3 类按 §4.3 判断值不值得做。
6. **验证（§2.4）**：选该子系统约 20 个历史提交，只给模型看地图，让它预测会动哪些节点，
   再与真实 diff 比较。预测准 → 本轮结束。预测不准 → 回到第 3 步，或者把它记成残差。

**停止条件**：主量达到预先设定的目标，并且所有残差都已经分类。

建议顺序：先做 7（事务）+ 9（WAL）+ I1/I2，这里痛点密度最高，外部参照也最成熟；
再做 11 + I4；然后 4/5 + I6；最后补齐其余子系统。

### 10.1 格式约定（为以后迁移和可视化留好接口，现在不做工具）

长期计划：这些内容以后会迁到一个单独的仓库，并做可视化。短期只关注抽象本身，
但下面几条从第一阶段起就要遵守，这样以后可以直接解析成图，不需要返工：

- **稳定 ID**：环境前提 `E<n>`；力 `F<n>`；决策 `D-<slug>`；不变量 `I1`–`I8`；子系统 `S01`–`S12`；L1 模块 `S07.M03`；
  原则 `R<n>`；残差 `X<n>`。ID 一旦分配就不再改，删除时标为废弃。
  力是推导链的根节点，决策和卡片都要引用它，所以和其他节点一样有 ID。当前是 F1 正确性与持久性、F2 并发、
  F3 可扩展性、F4 性能、F5 兼容性、F6 可移植性、F7 可维护性；定义归 `principles.md`，在它写出来之前暂存 `L0.md` §2.1。
- **引用写法统一**：节点之间用 `[[S07.M03]]`、`[[I1]]`、`[[D-idx-am]]` 互相引用。
  证据统一写成 `commit:<hash>`、`file:<path>:<line>`、`readme:<path>#<章节>`、
  `url:<链接>`。
- **每个文件开头加简短的 YAML 头**，只放 `id`、`type`、`depends`、`invariants`
  这几个能直接变成图上边的字段；正文仍然是写给人读的 Markdown。
- 只用纯文本和 Markdown，图用 Mermaid 或纯文字描述，不依赖任何特定工具。
