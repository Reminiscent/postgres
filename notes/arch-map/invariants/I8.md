# I8 兼容性

## 1. 不变量

在发布类别允许的范围内，新二进制能读懂旧数据（数据目录、WAL、pg_control、各类状态文件、线上协议），按较早小版本编译的扩展在较新的小版本里继续工作；超出范围的不兼容必须被版本号检出并拒绝，不能被误读。

适用条件（有意放松或不适用）：
- 大版本之间：catalog、WAL、pg_control、内部 API/ABI 都可以变，只要求 pg_upgrade 或 dump/reload 能升级；用户数据文件只在"能原样读"或"pg_upgrade 会转换/拒绝"时才算兼容 〔[[D-compat-by-release-class]]; file:doc/src/sgml/ref/pgupgrade.sgml:49-57〕。
- 开发分支内部：格式可以随时变，只要求提升对应版本常量，让旧数据目录被拒绝而不是被误读 〔file:src/include/catalog/catversion.h:6-29〕。
- 小版本之间：只承诺"旧小版本编译的扩展在新小版本里工作"，反方向不保证；安全修复和少数正确性修复可以触及 ABI，但要逐条写明（T7 及其反例；另见 §7 的 commit:45c357e0e85）。
- 主备不同小版本：只是"很可能可行"，没有正式支持；新小版本读旧小版本的 WAL 比反过来更可能成功，所以先升级备库 〔file:doc/src/sgml/high-availability.sgml:599-610〕。
- 跨硬件架构、跨编译参数：不兼容，由 pg_control 在启动时拒绝（[[S09.M02]] Inv(8)）；但 C 的 char 符号性曾漏记，见 I8.R5。
- 扩展 ABI 的服务器侧"边界"本身没有明确定义；大部分内部接口不是为扩展长期稳定设计的 〔file:doc/src/sgml/xfunc.sgml:2900-2906〕。

## 2. 由什么推出

- [[D-compat-by-release-class]]：小版本不改磁盘格式和 ABI，大版本可以改（根决策；配套 T7、R5）。
- [[D-wal-self-describing]]：WAL 记录格式统一、带页魔数。
- [[D-proto-minor-negotiation]]：minor 协议版本与 `_pq_.` 选项走协商。
- [[D-fmgr-v1]]：所有 C 函数一个调用约定，扩展库加载时校验 magic block。
- [[D-idx-am]] [[D-table-am]]：AM 能力由 handler 返回的 C 结构体表达（结构体布局成为扩展 ABI）。
- [[D-xid-wraparound-freeze]]：元组头里的 xid 保持 32 位（与 F5 的关系是假设）。

## 4. 协议

**P1 启动时的兼容性检查顺序**（[[S09.M02]]）
1. 读 pg_control：先比 PG_CONTROL_VERSION（含字节序误判提示），再验 CRC，再比 catversion，再逐项比 MAXALIGN、浮点格式、BLCKSZ、RELSEG_SIZE、SLRU 段大小、XLOG_BLCKSZ、NAMEDATALEN、INDEX_MAX_KEYS、TOAST 块大小、LOBLKSIZE 〔file:src/backend/access/transam/xlog.c:4519-4660〕。
2. 恢复读 WAL 时，每页比对 XLOG_PAGE_MAGIC 〔file:src/backend/access/transam/xlogreader.c:1350〕。
3. 装载槽、快照、复制源、pgstat、两阶段文件时各自比对版本常量（I8.R1 的锚点）。
- 顺序的作用：版本比对放在 CRC 之前，结构变了也能报"版本不符"而不是"CRC 错"；漏提 PG_CONTROL_VERSION 时只剩 CRC 失败可报（commit:99dd8b05aa5）。

**P2 开发分支上改一种持久格式**
1. 改代码，同一个提交里提升该格式自己的常量（I8.R1、I8.R2）。
2. 如果这种文件会被 pg_upgrade 原样搬运（I8.R5），同一个周期内在 pg_upgrade 里加转换，按新 catversion 门控（file:src/bin/pg_upgrade/pg_upgrade.h:105-115; commit:bd8d9c9bdfa），或加预检拒绝。
3. 如果改的是扩展可见的头文件，无需兼容，但已发布分支的回补要走 P3。
- 颠倒或漏掉第 2 步：升级后的集群带着旧格式文件运行（C2）。

**P3 往已发布分支回补触及格式或 ABI 的修复**
1. WAL：不改记录格式；重放代码必须兼容旧小版本写出的记录，开发分支同时提升 XLOG_PAGE_MAGIC 用干净写法（commit:789d65364cd）。
2. ABI：新成员塞进填充或加在末尾；被扩展当数组访问的结构体不能改大小；改原型时保留旧函数做包装（commit:6bfacd368bb; commit:66aaabe7a18）。
3. 做不到时只进开发分支；确需破坏的（安全修复、个别正确性修复）在提交信息里写明影响（T7；commit:45c357e0e85）。
- 运维侧：先升级备库，因为新小版本更可能读懂旧 WAL（file:doc/src/sgml/high-availability.sgml:603-610）。

**P4 pg_upgrade 的步骤顺序**（地图范围之外，src/bin/pg_upgrade/…；后端参与第 3 步）
1. 检查：二进制版本、控制文件参数、校验和、各类不可升级的对象和数据类型（check.c、controldata.c）。
2. 把旧集群的提交状态和 next xid 复制到新集群。
3. 以 binary upgrade 模式恢复 schema，预设 OID 和 relfilenumber（I8.R6）。
4. 拷贝或链接用户关系文件，必要时转换（I8.R5）。
- 证据：file:src/bin/pg_upgrade/IMPLEMENTATION:53-94。第 1 步必须覆盖所有会让第 3、4 步失败的情形，否则新集群在被改动后才失败（C4；commit:09878cdd489 的说明是"在做任何实质动作之前失败"）。

**P5 启动包与协议版本协商**（[[S02.M01]]）
1. 客户端发启动包，带协议版本和可选 `_pq_.` 参数。
2. 后端解析；major 不支持即拒绝；minor 高于 PG_PROTOCOL_LATEST 或有未知 `_pq_.` 选项，回 NegotiateProtocolVersion，用双方都支持的版本继续 〔file:src/backend/tcop/backend_startup.c:875-885〕。
3. 之后进入认证。
- 旧于协商机制的服务器会直接拒绝更高 minor，所以客户端要能退回 3.0（commit:a60a103386a）。

## 5. 并发与失败语义

- error：协议读途中出错升级为 FATAL（I8.R10）；扩展加载校验失败报 ERROR 并拒绝加载（[[S12.M05]] Contract）；逻辑复制版本不符在启动阶段 ERROR（[[S10.M12]] Contract）；pg_upgrade 预检失败时不动新集群（P4）。
- crash：pg_control 每次整体重写且不大于一个扇区（[[S09.M02]] Inv(7)），崩溃后不会出现半新半旧的版本信息；其余状态文件的崩溃语义在各自卡片上（[[S10.M05]] Contract 等）。pg_upgrade 中途失败后旧集群仍可用，新集群需重建（file:src/bin/pg_upgrade/IMPLEMENTATION:96-98）；link 模式下启动新集群后旧集群不可再用（未核实细节）。
- cancel：取消在读消息途中到达同 error（I8.R10）；其他情形未定义。
- standby：主备不同小版本没有正式支持；新小版本备库应能重放旧小版本主库的 WAL（I8.R3），反之不保证。跨架构的物理复制本就不支持（file:doc/src/sgml/high-availability.sgml:595-596），char 符号性问题（C11）出现在这条边界附近。
