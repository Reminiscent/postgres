# I6 语义等价

## 1. 不变量
解析、改写、规划和执行对查询所做的任何变换、证明和捷径都不改变查询结果：`equal()` 的两个表达式在使用处是同一个值，变换所依赖的相等关系、可空性、求值次数、安全顺序与原查询一致，交给 worker 执行的部分确实是并行安全的。

适用条件：
- 并行安全只按 `pg_proc.proparallel` 标注判定，标注错了不在本不变量保证范围内（见 [[S04.M05]] Inv(5)；`file:src/backend/optimizer/plan/planner.c:447-457` 称这种情况是"函数标注错误或规划器的 bug"）。
- volatile 函数的"求值次数"只在查询明确规定时才受保护；EC 推理不收 volatile 表达式（`file:src/backend/optimizer/README:875-877`），HAVING 只在不含 volatile 时才移到 WHERE（`file:src/backend/optimizer/plan/planner.c:1248-1251`）。
- 基于 collation 的相等：两个 collation 都是 deterministic 时可视为同一个相等关系（`file:src/backend/optimizer/plan/analyzejoins.c:808-810`）；nondeterministic collation（PG 12 起）下这一放松不成立；分区连接也不用这一放松，要求子句的 collation 与分区键 collation 完全相同（`file:src/backend/optimizer/util/relnode.c:2510-2512`，见 I6.R5）。
- 统计信息只影响计划选择，不在结果等价的保证之内，但读者必须容忍任意统计值（[[S04.M11]] Inv(3)）。
- C 代码可以绕过并行模式的禁写检查（[[S01.M06]] Contract 的泄漏）。

## 2. 由什么推出
- [[D-var-nullingrels]]：Var 携带可能把它置 NULL 的外连接集合（留出集决策）
- [[D-equivalence-class]]：用 EC 表示传递相等
- [[D-pathkeys]]：排序性质引用 EC，canonical 后指针比较
- [[D-view-rls-as-rewrite]]：视图与 RLS 以 Query 树变换实现
- [[D-parallel-copy-state]]：并行只复制选定状态并禁写
- [[D-path-plan-split]]：先枚举等价的 Path 再按代价选

## 4. 协议

### P1 表达式语义属性的确定与使用顺序
1. [[S03.M02]] 解析分析建表达式，随后 assign_query_collations 后处理为每个节点写输出 collation 与 inputcollid；Var 按语法位置初标 varnullingrels。
2. [[S03.M05]] [[S03.M06]] 改写展开视图并把 RLS 策略前置到 securityQuals。
3. [[S04.M01]] 预处理表达式（eval_const_expressions：插入默认参数、内联、折叠）。只有这一步之后，volatile/mutable、并行安全、可空性判定才可靠（R6）。
4. [[S04.M02]] 上拉、外连接化简、qual 分发；建 EC，按 security_level 标记 qual；外连接交换时为 qual 生成带 incompatible_relids 的 clone。
5. [[S04.M01]] 宣布 EC 合并完成（ec_merging_done）；之后才建 canonical PathKey（R4）。
6. [[S04.M03]] 枚举 Path，消费 EC、唯一性证明（R5）、consider_parallel（R12）。
7. [[S04.M07]] 生成 Plan，setrefs 按 nullingrels 精确匹配引用（R1），按 security_level 排 qual 顺序（R8）。

顺序颠倒的后果：在第 3 步之前判断 volatility 会把 `default now()` 或可内联的函数判错（commit:743ddafc712）；反过来，在折叠之后判断并行安全会把已被折叠成常量的 parallel-unsafe 函数当成安全（commit:eae7be600be）。所以"先预处理再判定"并不处处适用：判定的对象必须是实际要执行的表达式。证据：`file:src/backend/optimizer/util/clauses.c:548-560`；`file:src/backend/parser/parse_collate.c:6-21`；`file:src/backend/optimizer/plan/planmain.c:204`。

### P2 并行计划从标注到执行
1. [[S04.M01]] 判 parallelModeOK（扫描整个查询的最高并行风险）；为假则后续不设任何 consider_parallel（`file:src/backend/optimizer/plan/planner.c:424-457`）。
2. [[S04.M03]] 对每个 rel 判 consider_parallel，只为它生成 partial path；partial path 只能被 Gather/GatherMerge 收拢（`file:src/backend/optimizer/README:1426`）。
3. [[S04.M07]] 生成 Plan；任何把 initPlan 移到节点上的操作同时清该节点 parallel_safe（`file:src/backend/optimizer/plan/setrefs.c:1610-1616`）。
4. [[S05.M10]] 只序列化 parallel_safe 子计划（`file:src/backend/executor/execParallel.c:201-216`），进入并行模式。
5. [[S01.M06]] 复制 GUC、快照、xid 集合、combo CID 等状态给 worker；此后禁止写与分配 xid（R13）。

R12 在第 3 步之后才对计划成立；第 3 步漏清标记，第 4 步会把引用未下发 initPlan 的子计划送进 worker（commit:88ceac5d77f）。

## 5. 并发与失败语义
- error：本族状态几乎全在单次规划的内存上下文里，随之回收（[[S04.M05]] Contract 标为假设）。并行执行中 leader abort 时杀掉并等待全部 worker（[[S01.M06]] Contract）。
- crash：规划与表达式语义状态都不持久，无需恢复；worker 异常退出触发全局重置（[[S01.M06]]）。
- cancel：同 error；规划循环中有 CHECK_FOR_INTERRUPTS（[[S04.M05]] Contract）。
- standby：[[S04.M05]] 写"无差异（假设）"；[[S01.M06]] [[S05.M10]] [[S05.M12]] 写"未定义"。本文件不补充。
- 并发：规划器本身无跨后端状态。计划生成后 catalog 变化（约束改为 NOT VALID、collation/opfamily 变化、函数重新标注）使 R2/R5/R12 的前提失效，由计划缓存失效负责重规划（[[I4]]，[[S02.M06]] Inv(1)）；环境变化见 R14。
