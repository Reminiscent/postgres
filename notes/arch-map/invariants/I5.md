# I5 资源生命周期

## 1. 不变量
任何退出路径（ERROR 的 longjmp、（子）事务中止、FATAL 与进程退出）都能释放该路径负责的全部资源，且释放过程本身不会再出错；临界区内的错误一律升级为 PANIC，交给崩溃重置。

适用条件：
- 不在事务内（或在失败事务内）时 CurrentResourceOwner 为 NULL，不得获取查询期资源；辅助进程改用 AuxProcessResourceOwner。file:src/backend/utils/resowner/README:63-68; file:src/backend/utils/resowner/resowner.c:1003-1011
- 没有异常处理者（后端启动期等）时 ERROR 升为 FATAL，走进程退出路径而不是事务中止（[[S12.M03]] Inv(2)）。
- PANIC 与 SIGQUIT 不做任何清理，共享状态由 postmaster 的整体重置回收（[[I7]]；[[S01.M07]] Inv(4)）。
- 单用户模式读命令时 die() 直接处理中断，不等安全点（[[S01.M04]] Inv(1)）。
- 有意活过事务的资源不受"事务结束释放"约束：已加载的库永不卸载（[[S12.M05]] Inv(3)）；typcache、ts_cache 条目随后端存活（[[S11.M10]] Inv(2)(5)）；dsm_pin_segment / dsa_pin / dsa_pin_mapping 的段与映射（[[S01.M03]] Inv(3)、[[S12.M02]] Inv(1)(2)）；WITH HOLD 游标（[[S02.M05]] Inv(2)）。它们的释放点各自定义在卡片上。
- 临界区内"只在允许的上下文分配"只是 Assert，非 cassert 构建不检查。file:src/backend/utils/mmgr/mcxt.c:198-199

## 2. 由什么推出
- [[D-error-longjmp-abort]]：出错不逐层返回，清理集中在（子）事务中止。
- [[D-memory-context]]：内存按生存期整树回收。
- [[D-resource-owner]]：非内存资源按事务/子事务/portal 记账回收。
- [[D-signal-flag-latch]]：信号只置标志，中断在安全点才处理。

## 4. 协议

### P1 ERROR 的恢复
1. 出错代码 ereport(ERROR)；errfinish 清零 InterruptHoldoffCount、QueryCancelHoldoffCount、CritSectionCount，把 CurrentMemoryContext 留在 ErrorContext，longjmp 到最近的 PG_exception_stack。file:src/backend/utils/error/elog.c:530-557
2. 若落在 PG_CATCH：处理者要么 PG_RE_THROW（回到第 1 步的外层），要么中止（子）事务（P5）。
3. 若落在顶层：PostgresMain 的 sigsetjmp 只做"仅属外层"的恢复，然后 AbortCurrentTransaction（P2）。file:src/backend/tcop/postgres.c:4570
- 第 3 步完成后 I5.R7、I5.R10、I5.R14 才成立；在此之前全局状态（当前上下文、owner、各模块的全局变量）都可能停在出错时的样子。
- 顺序颠倒：PG_CATCH 里既不重抛也不中止，后续代码在未清理的状态上运行（I5.R1）。

### P2 （子）事务中止的释放顺序
1. HOLD_INTERRUPTS，保证有可用的内存上下文和 owner（AtAbort_Memory、AtAbort_ResourceOwner）。file:src/backend/access/transam/xact.c:2877,2884-2885
2. 先放进程级短锁与等待状态：LWLockReleaseAll → WaitLSNCleanup → AIO 错误清理 → UnlockBuffers → ConditionVariableCancelSleep → LockErrorCleanup。注释给的原因：清理过程中可能再次去拿这些锁；锁管理器在等待未清理时再等锁会出错。file:src/backend/access/transam/xact.c:2887-2919
3. 并行、portal（AtAbort_Portals）、大对象、relmap 等模块的中止钩子；写 abort 记录，ProcArrayEndTransaction。file:src/backend/access/transam/xact.c:2977-3019
4. XactCallbacks，然后 ResourceOwnerRelease 三阶段，各阶段之间插入 buffer、relcache、inval 等 AtEOXact；最后 GUC、SPI、文件等 AtEOXact；RESUME_INTERRUPTS。file:src/backend/access/transam/xact.c:3031-3070
5. 稍后（顶层收到 ROLLBACK 或命令结束时）CleanupTransaction：清 portal 内存与快照，删 owner，最后 AtCleanup_Memory。file:src/backend/access/transam/xact.c:3076-3110
- 子事务中止是同一顺序的缩小版，只撤销本层：file:src/backend/access/transam/xact.c:5305-5440。
- 第 2 步之后才能安全地取锁、分配；第 5 步之前事务级内存仍在，中止钩子可以读它。
- 顺序颠倒：先跑回调再放 LWLock，回调可能自锁死；先删内存再释放 owner，ReleaseResource 回调访问已释放内存。

### P3 提交时的资源释放
1. 提交前的用户代码阶段（延迟触发器、holdable 游标物化）。
2. XactCallbacks 之后先把 CurrentResourceOwner 置 NULL，再按三阶段 ResourceOwnerRelease(isCommit=true)，锁在 LOCKS 阶段由 ProcReleaseLocks 统一释放。file:src/backend/access/transam/xact.c:2455-2497
3. 释放时仍登记在 owner 上的资源按泄漏逐个 WARNING（[[S12.M04]] Inv(4)）。
- 顺序颠倒：第 2 步之后还用 CurrentResourceOwner 登记资源，会碰到"释放已开始"的错误（commit:c21e6e2fd48）。

### P4 进程退出
1. proc_exit_prepare：置 proc_exit_inprogress，清零临界区计数与错误上下文栈。file:src/backend/storage/ipc/ipc.c:166-194
2. shmem_exit：先 LWLockReleaseAll；再逆序跑 before_shmem_exit（含 ShutdownPostgres → AbortOutOfAnyTransaction，所以 FATAL 时事务内资源仍走 P2）；再 dsm_backend_shutdown 跑各段的 detach 回调；再 on_shmem_exit（ProcKill 等）。file:src/backend/storage/ipc/ipc.c:229-275; file:src/backend/utils/init/postinit.c:878,1398-1401
3. on_proc_exit 回调。file:src/backend/storage/ipc/ipc.c:205-217
- 每个回调在调用前从表中摘除，回调本身出错不会死循环。
- PG_ENSURE_ERROR_CLEANUP 的回调是临时登记的 before_shmem_exit，后登记先执行，早于 ShutdownPostgres。file:src/include/storage/ipc.h:47-60
- 顺序颠倒：DSM detach 之后才放 LWLock，若锁位于 DSM 中即段错误（commit:9cbb1d21d67）。

### P5 内部子事务包裹（PL 的异常块等）
1. 保存 CurrentMemoryContext 与 CurrentResourceOwner；BeginInternalSubTransaction。
2. PG_TRY 内执行；成功则 ReleaseCurrentSubTransaction。
3. PG_CATCH 内：切回保存的上下文，CopyErrorData/FlushErrorState，RollbackAndReleaseCurrentSubTransaction。
4. 两条路径都把 CurrentMemoryContext 与 CurrentResourceOwner 恢复为保存值。file:src/pl/plpgsql/src/pl_exec.c:1828-1895
- 第 4 步之后 I5.R8 才成立。漏掉第 4 步：后续资源登记到已删除的子事务 owner（commit:7dcea51c2a4）。

### P6 临界区内改页并写 WAL
步骤见 [[S09.M01]] Inv(1)（[[I1]] 的协议）；本族只关心：进入临界区前必须做完所有可能失败的准备（[[S09.M01]] Inv(4)、[[S08.M13]] Inv(4) 截断前先算好各 fork 的大小，commit:38c579b0898）。

## 5. 并发与失败语义
- error：P1→P2。可靠回收的前提是资源已登记在 owner、上下文或某个 AtEO(Sub)Xact 钩子里（I5.R7、I5.R10、I5.R14）；只靠局部 PG_CATCH 清理的东西在 FATAL 时漏掉（I5.R2）。清理中再出错会再入 AbortTransaction，所以中止钩子要幂等、不分配（I5.R9）；错误栈超过 5 层升 PANIC（[[S12.M03]] Inv(7)）。
- crash：PANIC、SIGQUIT、硬崩溃都不跑任何清理；共享内存由 postmaster 重建，DSM 遗留段下次启动清理（[[S01.M03]] Inv(3)），文件层面的遗留靠 WAL redo（I5.R19）。spinlock 与 LWLock 不会被别的进程代为释放，只能靠整体重置（I5.R5）。
- cancel：取消在 CFI 处转成 ERROR，此后同 error；die 转成 FATAL，走 P4。持 LWLock、在临界区、在 HOLD_INTERRUPTS 段内都推迟（I5.R4）；等 LWLock 与 spinlock 时不可取消（[[S01.M05]] Inv(1b)）。
- standby：startup 进程不跑事务状态机；文件删除与统计条目删除在 redo 中按 commit/abort 记录执行（I5.R19）；standby 上的后端照常有事务，WAIT FOR LSN 等等待者同样受 I5.R14 约束（commit:5cdec423193）。startup 进程自身的资源记账方式，卡片写"未定义"，本文件未核实。
