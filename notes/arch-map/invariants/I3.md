# I3 锁与顺序

## 1. 不变量

每次访问或修改共享状态之前，都要按约定的层级和顺序取到足够强的锁（关系锁 → buffer pin → 内容锁；多把锁按约定顺序取），并且在锁的保护范围内重新确认状态；锁的模式必须和每一种需要排除的并发操作冲突，跨进程的互相等待只能出现在死锁检测看得到的重锁上。

适用条件（在这些情形下不变量被有意放松，或换成另一种机制保证）：
- **恢复期间（hot standby）**：普通后端只能取 ≤RowExclusiveLock 的对象锁，startup 进程代持主库传过来的 AccessExclusiveLock，startup 自己的 buffer 修改不取关系锁〔file:src/backend/storage/lmgr/lock.c:889-897; readme:src/backend/storage/lmgr/README#Locking during Hot Standby〕。startup 与查询之间的死锁不靠重锁死锁检测，而是由 standby.c 的超时加取消处理〔file:src/backend/storage/ipc/standby.c:611-614,781-788〕。
- **并行查询的 lock group**：同组进程之间的重锁互不冲突（关系扩展锁除外），以并行模式只读为前提〔[[S07.M07]] Inv(6)〕。
- **本地 buffer（临时表）**：不取内容锁，`ConditionalLockBuffer` 对本地 buffer 直接返回成功〔file:src/backend/storage/buffer/bufmgr.c:6651-6652〕；改由"只有本会话访问"保证（[[S08.M02]] Inv(1)）。
- **fast-path**：非共享关系的弱锁不进主锁表，死锁检测不看它们，前提是强锁计数为 0〔[[S07.M07]] Inv(3)(4)〕。
- **LWLock 与 spinlock**：不在死锁检测范围内，顺序只是约定（[[X6]] [[X41]]）。
- bootstrap 模式下建索引的调用方可以不持表锁〔file:src/backend/commands/indexcmds.c:686-692〕；单用户模式下锁规则是否另有放松：未核实。

## 2. 由什么推出

- [[D-lock-tiers]]：锁分 spinlock、LWLock、重锁三层，各有不同保障
- [[D-lwlock-no-deadlock-detect]]：LWLock 不做死锁检测，顺序只能靠约定
- [[D-lock-partition-fastpath]]：锁表分区加 fast-path
- [[D-deadlock-optimistic-wait]]：乐观等待，超时后才查死锁
- [[D-analyze-takes-locks]]：分析时就取锁
- [[D-rewrite-relock]]：改写前对旧树重新取锁
- [[D-row-lock-in-tuple-header]]：行锁记在元组头
- 另外与 [[D-sinval-with-locks]]（取锁即接收失效，归 [[I4]]）和 [[D-catalog-mvcc-heap]]（弱于 AEL 的 DDL 以 MVCC catalog 为前提）相交。

## 4. 协议

**P1 打开一个按名字引用的关系**（I3.R1–R3）
1. 名字查找：`RangeVarGetRelidExtended` 查出 OID。
2. 取关系锁（级别按 I3.R4/R5 一次取足）；`LockRelationOid` 在取锁时接收失效。
3. 若取锁期间处理过失效，回到 1 重查，直到结果稳定（[[S11.M04]] Inv(1)）。
4. `relation_open` 断言已持锁（file:src/backend/access/common/relation.c:70）；之后才读 relcache。
5. 读页：pin → 内容锁（file:src/backend/storage/buffer/README:7-26）。
- 第 3 步之后 I3.R3 才成立；省掉第 3 步会锁住一个已被改名或重建的旧对象。第 2 步晚于第 4 步，读到的定义可能在锁到之前已被并发 DDL 改掉。

**P2 中止时的释放顺序**（I3.R8 R10 R16）
1. `LWLockReleaseAll`（最先：清理过程可能再取这些 LWLock）。
2. `UnlockBuffers` 释放 buffer 内容锁；取消条件变量等待。
3. `LockErrorCleanup` 退出正在进行的重锁等待。
4. 写中止记录、`ProcArrayEndTransaction`、发失效，最后由 ResourceOwner 释放重锁。
- 证据：file:src/backend/access/transam/xact.c:2887-2919,2999-3043。重锁要到第 4 步才放，因为中止期间仍需持有它们（同一注释）。第 1 步若推后，清理代码再取同一把 LWLock 即自死锁。提交侧顺序见 [[S07.M01]] Inv(1)，事务内的锁转交见 I3.R16。

**P3 强锁申请者与 fast-path**（I3.R12）：先加强锁计数，再把匹配的 fast-path 锁迁入主表，最后在主表排队；顺序颠倒会让新的弱锁走 fast-path 绕过冲突检查。见 [[S07.M07]] Inv(3)，不在此复述。

**P4 standby 上的 AEL**（I3.R13）：主库取 AEL 写 WAL → startup 重放时代持 → 提交/中止 redo 在 sinval 之后释放，或 RUNNING_XACTS 清理孤儿锁。见 [[S07.M07]] Inv(7) 与 [[S07.M09]] Inv(1)–(3)。

**P5 VACUUM 与索引扫描**（I3.R14）：阶段 I 收集死 TID → 阶段 II 删索引项（nbtree 每个叶页取 cleanup lock）→ 阶段 III 把 heap 项置 UNUSED。颠倒 II/III 会让持 pin 的扫描回 heap 时拿到已被重用的 TID。见 [[S06.M07]] Inv(6)、[[S06.M12]] Inv(3)。

**P6 并发建索引的多事务协议**：见 [[S11.M12]] Inv(B1)，此处不复述；它依赖 I3.R12（真实加锁等待）。

## 5. 并发与失败语义

- **error**：LWLock 与 buffer 内容锁在 elog 恢复中自动释放（P2）；spinlock 没有自动释放，所以持有时不得报错（I3.R10）；重锁持有到事务（或子事务）结束（I3.R16）。
- **crash**：锁都在共享内存里，后端崩溃触发整体重置，锁状态随之重建（[[I7]]）；prepared 事务的锁在恢复时由 `lock_twophase_recover` 重新取得（file:src/backend/storage/lmgr/lock.c:4354）。持 spinlock 时硬退出不会触发重置，后来者等到超时 PANIC（[[S01.M05]] Inv(5)，例：commit:208ea05a51b）。
- **cancel**：持有 LWLock 或 spinlock 期间 cancel/die 被挂起，等待它们时也不响应；等待重锁时可以取消（file:src/backend/storage/lmgr/README:39-45）。因此长等待不应放在 LWLock 上。
- **standby**：只有 startup 改数据块（[[S09.M05]] Inv(2)）；startup 与查询的冲突由取消解决，startup 参与的死锁由 standby.c 在 deadlock_timeout 后检查（file:src/backend/storage/ipc/standby.c:611-614,781-788）。[[S07.M09]] Inv(1) "恢复不会陷入死锁"只对重锁之间成立，见报告。
