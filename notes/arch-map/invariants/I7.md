# I7 进程健壮性

## 1. 不变量

postmaster 不依赖可能已被子进程写坏的共享内存；任一子进程以"不干净"的方式退出，都会被识别为崩溃并触发整体重置（杀掉全部子进程、丢弃并重建共享内存、从 WAL 做崩溃恢复），而不是让 postmaster 跟着崩溃、卡死或带着坏状态继续运行。

适用条件（不变量在这些情形下不适用或被有意放松）：
- 单用户模式没有 postmaster，也就没有监护和重置；`WaitLatch` 的 postmaster 死亡断言只在 `IsUnderPostmaster` 时生效 〔file:src/backend/storage/ipc/latch.c:177-180〕。
- `restart_after_crash=off`，或崩溃者是 startup 进程（且不是被 postmaster 自己的 SIGQUIT 杀掉的）：杀掉全部子进程后 postmaster 直接退出，不重置 〔file:src/backend/postmaster/postmaster.c:3230-3251,2307-2353〕。
- 立即关机（immediate shutdown）进行中、或已经处于 FatalError 时，后续子进程的非零退出只更新记账，不再触发新一轮重置 〔file:src/backend/postmaster/postmaster.c:2840-2841〕。
- Windows 上退出码 128（ERROR_WAIT_NO_CHILDREN）不算崩溃 〔file:src/backend/postmaster/postmaster.c:2637-2648〕。
- 不碰共享内存的子进程不会把 PMChildFlags 置为 ACTIVE；dead-end 子进程没有槽 〔commit:a78af042701〕。syslogger 不处理 postmaster 死亡，它要等管道写端全部关闭 〔commit:cfdf4dc4fc9〕。
- 检测靠退出码和 dead man switch：一个进程如果在登记 ACTIVE 之前就改了共享内存、再以 0/1 退出，postmaster 发现不了（见 R3）。

## 2. 由什么推出

- [[D-postmaster-no-shmem]]：监护进程远离共享内存，子进程异常即整体重置。
- [[D-process-per-connection]]：进程隔离，一个后端出错不直接破坏其他后端的地址空间，因而能"杀掉重来"。
- [[D-signal-flag-latch]]：信号处理器只置标志（主归 [[I5]]；本族用到它的"退出类处理器"部分）。

## 4. 协议

### P1 崩溃检测与整体重置（[[X124]]）
1. 子进程（`InitProcess`）在真正使用共享内存之前，把自己的 PMChildFlags 置为 ACTIVE，并登记 `on_shmem_exit` 回调，退出时把它改回 ASSIGNED 〔file:src/backend/storage/lmgr/proc.c:406-412; file:src/backend/storage/ipc/pmsignal.c:283-300〕。
2. postmaster 回收子进程（`CleanupBackend`）：退出码不是 0/1 就算崩溃；接着释放槽，槽不是 ASSIGNED 也算崩溃 〔file:src/backend/postmaster/postmaster.c:2626-2632,2657-2668〕。从这一步起 R2 成立。
3. `HandleChildCrash` → `HandleFatalError`：向全部子进程发 SIGQUIT（`send_abort_for_crash` 打开时发 SIGABRT），置 FatalError，转入 PM_WAIT_BACKENDS，记下 AbortStartTime 〔file:src/backend/postmaster/postmaster.c:2746-2819〕。
4. 子进程收到 SIGQUIT 后 `_exit(2)`，不跑回调（R5）；5 秒内没退出的，postmaster 发 SIGKILL（`send_abort_for_kill` 时发 SIGABRT）〔file:src/backend/postmaster/postmaster.c:1777-1792〕。
5. 全部子进程退出（PM_NO_CHILDREN）之后：如果是 startup 进程崩溃，或 `restart_after_crash=off`，postmaster 退出（R12）〔file:src/backend/postmaster/postmaster.c:3230-3251〕。
6. 否则按顺序：可选地删除临时文件 → `ResetBackgroundWorkerCrashTimes`（R11）→ postmaster 自己 `shmem_exit(1)`，其中会删除全部 DSM 段 → 重读控制文件 → 重跑 request 回调并重建主段 → 回到 PM_STARTUP，启动 startup 进程做崩溃恢复，重新接受连接 〔file:src/backend/postmaster/postmaster.c:3256-3297; file:src/backend/storage/ipc/dsm.c:368-381〕。从这一步起 R6 成立。
- 顺序颠倒的后果：在第 5 步之前就重建，存活进程还会写旧段；第 6 步如果从旧段读输入，就违反 R6（commit:ec9e05b3c39、commit:c3cc2ab87d7）；漏掉对 bgworker 的处理，worker 就不会重启（commit:b5d084c5353）。

### P2 启动包阶段到登记 ACTIVE 的交接（R3）
1. fork 出的连接子进程装上 SIGTERM 和启动包超时的处理器，二者都 `_exit(1)`；SIGQUIT 走 `_exit(2)` 〔file:src/backend/tcop/backend_startup.c:199-212〕。
2. 读启动包。这一阶段不碰共享内存；收到的取消请求只先存进 `cancel_req` 〔file:src/backend/tcop/backend_startup.c:163,309〕。
3. 关掉超时、屏蔽 SIGTERM，检查此时还没有登记任何 shmem 退出回调 〔file:src/backend/tcop/backend_startup.c:368-379〕。
4. 这之后才转发取消请求（要取 `pss_mutex`）〔file:src/backend/tcop/backend_startup.c:382-388〕，然后进入 `InitPostgres`/`InitProcess`，登记 ACTIVE。
- 第 4 步挪到第 3 步之前，就是 commit:208ea05a51b 修的那个 bug：处理器可能在持有 spinlock 时 `_exit(1)`，postmaster 却认为是正常退出。

### P3 postmaster 死亡
1. postmaster 持有每个子进程"死亡管道"的写端（有条件的平台上还配合父进程死亡信号）〔commit:89fd72cbf26; file:src/backend/storage/ipc/pmsignal.c:96-123,361〕。
2. 子进程的每个 latch 等待都带上死亡事件；`WL_EXIT_ON_PM_DEATH` 会让进程直接退出（R9）。
3. 新 postmaster 启动时，如果旧 SysV 段仍有进程挂接，就拒绝启动（[[S01.M03]] Inv(5)）。所以第 2 步是第 3 步不会永远卡住的前提。

## 5. 并发与失败语义

- error：子进程的 ERROR 留在进程内处理；没有处理者时升为 FATAL、退出码 1，按正常退出处理（[[S12.M03]] Inv(2)，R2）。在 postmaster 里，ERROR 就等于 postmaster 退出（R8）。临界区里的 ERROR 升为 PANIC → abort() → 整体重置（[[S12.M03]] Inv(1)）。
- crash：子进程见 P1。postmaster 自己崩溃不在本族保护之内：子进程按 P3 退出，下一次启动走崩溃恢复；DSM 残留段在下次启动时清理（[[S01.M03]] Inv(3)）。
- cancel：取消只把查询变成 ERROR，不影响本族；启动包阶段的取消转发见 P2。卡片上 [[S01.M03]] 的 cancel 一项写的是"未定义"。
- standby：PM_RECOVERY/PM_HOT_STANDBY 下普通子进程崩溃同样走 P1（[[S01.M01]] Contract）；startup 进程自己崩溃按 R12 退出，不重试。提升时，startup 进程要等 slotsync 等进程退出，依赖 R10（commit:db93032a7cb）。[[S01.M05]]、[[S02.M01]] 的 standby 一项卡片写的是"未定义"。

## 6. 改动检查单

| 如果改动…… | 必须检查 | 对应规则 | 漏掉的后果 |
|---|---|---|---|
| 在 `postmaster.c`/`pmchild.c`/`pmsignal.c`/`bgworker.c` 的 postmaster 侧代码里读写共享结构 | 决策只依据本地副本；不取锁、不取 spinlock；共享值被写坏时最多误判"谁崩溃了"，不能让 postmaster 崩溃 | R1 | 类别"postmaster 依赖共享内存" |
| 新增一块共享内存结构，或改 shmem request/init 回调 | 回调能在崩溃重置时重跑；不保留指向旧段的指针；需要跨重置保留的输入放在 postmaster 本地内存 | R6 | 重置后崩溃，或访问已不存在的地址 |
| 新增一种 postmaster 子进程，或新的启动时机（尤其是 PM_STARTUP 期间） | 槽池大小与 PGPROC freelist 对应；fork 失败按崩溃处理；P1 第 3 步要把它算进去；startup 失败的路径也要先杀掉它 | R7 R2 R12 | 孤儿进程；postmaster 崩溃（commit:9b43e6793b0） |
| 在 postmaster 进程中执行的检查（GUC、hba、启动 worker 前的配置校验） | 只报 LOG 并保留旧值，不报 ERROR | R8 | 一个配置错误让整个服务器关闭 |
| 改某个进程的 SIGQUIT/SIGTERM 处理器，或新写一个 | 只置标志、SetLatch，或 `_exit()`；不调 `exit`/`proc_exit`/`ereport`；不读可能由 spinlock 实现的原子量；SIGQUIT 统一用 `SignalHandlerForCrashExit` | R4 R5 | 处理器里死锁，进程退不出 |
| 改后台进程的 `sigsetjmp` 错误恢复块或信号掩码 | 错误恢复后 SIGQUIT 仍然没有被屏蔽 | R5 | 重置变慢，只能靠 SIGKILL |
| 把要碰共享内存的操作（取 spinlock/LWLock、写 ProcSignal）挪到连接启动早期，或挪到任何 `_exit(1)` 处理器还生效的阶段 | 先撤掉或屏蔽那些处理器；或者等登记 ACTIVE 之后再做 | R3 | 持锁退出却被当作正常退出，之后 PANIC（commit:208ea05a51b） |
| 扩展或后台代码直接调用 `exit()` | 碰过共享内存的进程一律走 `proc_exit` | R2 | dead man switch 会把它判成崩溃，触发整体重置 |
| 新增一个等待点（WaitLatch、条件变量、等远端回复、socket 读写） | 带 `WL_EXIT_ON_PM_DEATH`；能被关机/提升的信号打断；socket 写用非阻塞方式，并且在等待时检查超时 | R9 R10 | 孤儿进程；关机或提升时挂起 |
| 在关机路径上等待某个条件成立（例如 WAL 全部刷出） | 这个条件在关机期间保证会成立 | R10 | 关机时忙等，永远结束不了（commit:6eedb2a5fd8） |
| 在会调用 `system()`/`popen()` 的进程里改信号处理器 | 处理器经 pqsignal 安装，由包装处理器比较 `MyProcPid` 和 `getpid()`；fork 之后先更新 `MyProcPid` | R13 | PGPROC 数组损坏，或误报 PANIC |
| 改 bgworker 注册的记账，或在 DDL 路径上停 worker | 重置路径清掉每轮状态；停 worker 时，按是否允许重启，在"发信号"和"置 terminate 位"之间二选一 | R11 | worker 不再重启，或被永久注销 |
