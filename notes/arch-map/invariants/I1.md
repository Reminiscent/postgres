# I1 持久性

## 1. 不变量

已向客户端确认提交的事务，其效果在崩溃后仍在：数据页（以及 SLRU 页、控制文件、slot 等持久状态）落盘之前，描述它的 WAL 已经落盘；从任一 checkpoint 的 redo 点重放，得到的页与原操作的结果一致。

适用条件（在这些情况下不变量不适用或被有意放松）：
- unlogged 表及其索引不写 WAL，崩溃后被截断为空，也不复制到备库〔file:doc/src/sgml/ref/create_table.sgml:226-236〕；临时表同样不写 WAL（`RelationNeedsWAL` 为假）。
- `fsync=off`：不保证持久，操作系统或硬件崩溃后可能不可恢复〔file:doc/src/sgml/config.sgml:3322〕。
- `synchronous_commit=off`：最近的提交可能在崩溃后丢失，但数据库仍一致；丢失窗口约 3×wal_writer_delay〔readme:src/backend/access/transam/README#Asynchronous Commit〕。
- `full_page_writes=off`：撕裂页不能被修复，只在存储保证整页原子写时安全〔file:doc/src/sgml/config.sgml:3594〕。
- `wal_level=minimal`：新建 relfilenumber 上的改动不写 WAL，改为提交前 fsync 或整文件写 FPI；这类 WAL 不能用于 PITR 和增量备份〔readme:src/backend/access/transam/README#Skipping WAL for New RelFileLocator〕。
- `data_sync_retry=on`：fsync 失败不 PANIC，持久性取决于内核是否保留了脏页〔file:src/backend/storage/file/fd.c:3970-3989〕。
- hint（hint bit、FSM 等）按设计可以丢失，只在开启校验和或 wal_log_hints 时因防撕裂页而写 FPI；开启时，恢复中或对 WAL 跳过的关系（wal_level=minimal 下的新 relfilenumber），MarkBufferDirtyHint 只设 hint、不弄脏页（只限 hint，非 hint 改动见 I1.R5）〔readme:src/backend/access/transam/README#Writing Hints; file:src/backend/storage/freespace/README:171; file:src/backend/storage/buffer/bufmgr.c:5760-5772〕。
- 恢复期间不写 WAL，"WAL 先于数据"改由 minRecoveryPoint 体现（见 I1.R14）〔file:src/backend/access/transam/xloginsert.c:165-166〕。
- 文件系统动作（建/删文件、目录、数据库、表空间）不能放进临界区，按"先做、成功后写 WAL"或"先写 WAL、失败只 WARNING"处理，可能留下孤儿文件〔readme:src/backend/access/transam/README#Write-Ahead Logging for Filesystem Actions〕。

## 2. 由什么推出

- [[D-wal-redo-only]]：只做 redo，提交只需刷 WAL
- [[D-full-page-writes]]：redo 点后首次修改带整页镜像
- [[D-hint-wal-checksum]]：开校验和时 hint 也要防撕裂
- [[D-fsync-fail-panic]]：fsync 失败不重试
- [[D-replication-slot]]：为落后的消费者保留 WAL
- [[D-origin-progress-in-commit]]：apply 进度随本地 commit 记录持久化
- [[D-relmapper]]：mapped catalog 用独立 map 文件定位
- [[D-wal-archive-pitr]]：归档与 timeline

## 4. 协议

**P1 改页并写 WAL**〔readme:src/backend/access/transam/README#Write-Ahead Log Coding〕
1. 调用者（AM）：pin 并排他锁住要改的所有 buffer；在临界区外检查空间等可能出错的条件，必要时 XLogEnsureRecordSpace（它断言不在临界区，file:src/backend/access/transam/xloginsert.c:194）。
2. 调用者：START_CRIT_SECTION。
3. 调用者：改页。
4. 调用者：MarkBufferDirty（必须在插入记录前，否则 checkpoint 可能在记录与弄脏之间开始而漏刷该页）。
5. 调用者：XLogBeginInsert、XLogRegisterBuffer（每个改过的 buffer）、XLogInsert；[[S09.M01]] 决定是否附 FPI（I1.R3）。调用者以返回 LSN 做 PageSetLSN。
6. END_CRIT_SECTION，解锁、unpin。
- 第 5 步之后 I1.R1 才对该页成立（页 LSN 指向描述它的记录）。
- 颠倒：4 与 5 颠倒 → checkpoint 漏刷；5 在锁外取数据 → 记录内容与页不一致（commit:d42c5457e51）；2 在 1 之前分配内存 → 断言/PANIC（commit:56b662523fd）。

**P2 提交**〔见 [[S07.M01]] Inv(1)(2)〕
1. 事务状态机：置 DELAY_CHKPT_IN_COMMIT，插入 commit 记录（含待删文件清单、origin 进度、失效消息）。
2. 同步提交：XLogFlush 到 commit LSN；异步提交：只在 clog 记下 LSN。
3. 写 clog，清 DELAY_CHKPT_IN_COMMIT。
4. 同步复制等待（[[S10.M04]] Inv(1)），仍持锁。
5. ProcArrayEndTransaction（对他人可见）、发 sinval、释放锁；之后执行待删文件的删除（[[S08.M13]] Inv(1)）。
- 第 2 步之后提交才持久；第 4 步之后才对他人可见，所以别人看到的提交在本机已持久。
- 颠倒：先可见后刷盘 → 他人基于一个崩溃后会消失的提交做了决定；先删文件后提交 → 中止后文件已没了。

**P3 checkpoint**〔见 [[S09.M03]] Inv(1)(2); file:src/backend/access/transam/xlog.c:8403-8434〕
1. checkpointer：插入 XLOG_CHECKPOINT_REDO，其起点即 redo 点；更新 RedoRecPtr（此后首次改页带 FPI）。
2. 等待所有置了 DELAY_CHKPT_START 的进程（它们的 WAL 在 redo 点前、改动可能尚未进 buffer）。
3. CheckPointGuts：relmap、origin、SLRU、buffer 写出，然后 ProcessSyncRequests 统一 fsync；随后 slot、snapbuild、rewrite 映射、2PC 状态落盘。
4. 写 checkpoint 记录并刷盘；更新 pg_control（checkPoint、checkPointCopy）。
5. 计算保留界（I1.R18），失效超限的 slot，回收旧段。
- 第 4 步之后才可以说"从新 redo 点重放就够了"；第 5 步只能在第 4 步之后。
- 颠倒：先回收后更新 pg_control → 崩溃后 redo 点所在段已不存在（commit:7863ee4def6）；第 3 步漏刷某子系统 → 它在 redo 点之前的改动既不在盘上也不会被重放（commit:6c46e8a5dfc 的同类）。

**P4 截断关系**〔见 [[S08.M13]] Inv(4)〕
1. 持 AccessExclusiveLock，置 DELAY_CHKPT_START/COMPLETE。
2. 写截断 WAL 并无条件刷盘。
3. 临界区内：丢弃截断范围的 buffer（即使脏），smgrtruncate；失败即 PANIC。
- 颠倒：先丢 buffer、截文件失败 → 旧版本从磁盘复活（commit:38c579b0898）；checkpoint 夹在中间 → 重放从 checkpoint 开始时看到不该有的页（commit:412ad7a5563）。

**P5 崩溃恢复与 unlogged 重置**〔file:src/backend/access/transam/xlog.c:6473-6479,6621-6629; file:src/backend/storage/file/fd.c:3573-3590〕
1. startup：崩溃后先对整个数据目录 fsync（[[S08.M07]] Inv(6)）。
2. 删除 unlogged 关系除 init fork 外的 fork（[[S08.M08]] Inv(1)）。
3. 从 redo 点重放；redo 改了 init fork 立即刷盘（I1.R16）；写出的页推进 minRecoveryPoint。
4. 到达一致点后才放只读连接（I1.R14）。
5. 恢复结束：从磁盘上的 init fork 复制出主 fork 并 fsync；必要时写 OVERWRITE_CONTRECORD、切新 TLI（I1.R20 I1.R21），写 end-of-recovery checkpoint。
- 颠倒：第 3 步的 init fork 改动留在 buffer → 第 5 步复制到旧内容（commit:8e684ce11dd）。

## 5. 并发与失败语义

- **error**：P1 的临界区内出错一律 PANIC，靠崩溃恢复丢掉 buffer 里未记 WAL 的改动（I1.R2；"以 redo 代替撤销"作为原因是假设，见 [[X99]]）。截断同样在临界区内（I1.R13）。文件系统动作在临界区外，出错可留孤儿文件，删除失败只 WARNING（§1）。提交写 WAL 后、clog 前出错同样 PANIC（[[S07.M01]]）。
- **crash**：已刷盘的 WAL 决定结果；没有提交记录的事务视为中止，不需 undo（[[D-wal-redo-only]]）。撕裂页靠 FPI 修复（I1.R3），不完整的尾记录由 I1.R20 处理。fsync 失败 PANIC 后从 WAL 重做（I1.R9）。
- **cancel**：临界区内持有中断，cancel 不会打断 P1/P4；截断丢 buffer 时等待 IO 曾可被取消，现已移入临界区（commit:38c579b0898）。RegisterSyncRequest 的重试循环不检查中断（[[X50]]）。
- **standby**：只有 startup 改数据块（I1.R15）；备库不写 WAL，用 restartpoint 代替 checkpoint，用 minRecoveryPoint 代替 WAL-before-data（I1.R14）；walreceiver 只让 startup 重放已 fsync 的部分（I1.R19）。提升时与正在进行的 restartpoint 的交互是 bug 多发处（§7 第 7 类）。卡片上"未核实"的项：无新增。
