# I4 缓存一致性

## 1. 不变量
catalog 变更提交后，任何后端在下一次对受影响对象取得冲突锁（或开始下一个事务）时，必须已丢弃或标记所有依赖该变更的本地缓存与派生状态，且不在可能处理失效的点之后继续使用已失效的数据。

适用条件（有意放松或不成立的情形）：
- 已持有所需锁时 `LockRelationOid` 不再接收失效，可能漏看变更（[[X72]]；file:src/backend/storage/lmgr/lmgr.c:117-139）。
- GRANT/REVOKE 不对目标表加锁，`relation_openrv` 因此即使已持锁也先接收失效；`NoLock` 打开假定本命令前面已接收过（file:src/backend/access/common/relation.c:142-154）。
- 弱于 AccessExclusiveLock 的 DDL：多数派生缓存在构建期可能"生而过时"，变更可能永远读不到；只有 relcache（以及 catcache、evtcache）有重试或保持"需重建"（file:src/backend/utils/cache/inval.c:68-80；[[X73]]）。
- 本事务自己的修改不经 sinval，而在 CommandCounterIncrement 时本地应用；同一命令内旧元组仍"有效"（file:src/backend/utils/cache/inval.c:8-22）。
- 逻辑解码中缓存对应的是被解码事务时刻的 catalog（历史快照），不是当前 catalog（[[S10.M09]] Inv(4)）；inplace 更新在解码中可能早于快照可见（readme:src/backend/access/heap/README.tuplock#Reading inplace-updated columns）。
- 临时表等会话本地对象照样发失效，不做区分（file:src/backend/utils/cache/inval.c:88-95）。

## 2. 由什么推出
- [[D-sinval-with-locks]]：共享失效队列，与重锁捆绑。
- [[D-plancache-lazy-inval]]：计划失效只标记，下次使用时重做。
- [[D-utility-late-analysis]]：utility 语句推迟到执行时分析，避免缓存的分析结果过期。
- [[D-rls-env-replan]]：RLS 环境变化时由计划缓存重做改写。
- 上游：[[D-catalog-driven-extensibility]]（每个后端必须缓存 catalog）、[[D-catalog-mvcc-heap]]（命令内不 flush、catalog 快照随失效作废）。

## 4. 协议

### P1 事务性 catalog 变更的失效（产生 → 本地 → 广播 → 接收）
1. DDL 经 heap_insert/update/delete 改 catalog 行；heapam 调 `CacheInvalidateHeapTuple` 登记到 CurrentCmd 列表（file:src/backend/access/heap/heapam.c:2207）。依赖不在这几个 catalog 的，DDL 自己调 `CacheInvalidateRelcache*`（I4.R3）。
2. CommandCounterIncrement：`CommandEndInvalidationMessages` 本地应用并移入 PriorCmd；wal_level=logical 时写失效 WAL（file:src/backend/utils/cache/inval.c:1403）。此后本事务看到新状态（I4.R4）。
3. 提交：写提交记录（带失效消息）→ ProcArrayEndTransaction → `AtEOXact_RelationCache` → `AtEOXact_Inval(true)` 先删 init file、发 SI → 释放锁（file:src/backend/access/transam/xact.c:2441-2495）。此后 I4.R1 成立。
4. 读方：取锁（非 ALREADY_CLEAR）或事务开始时 `AcceptInvalidationMessages`（file:src/backend/storage/lmgr/lmgr.c:134-138），先 catcache 后 relcache、再调高层回调。I4.R2 由此成立。
- 颠倒的后果：先发 SI 后写提交记录，其他后端重读时看不到新元组又重新装入旧值（file:src/backend/utils/cache/inval.c:30-33）；先放锁后发 SI，等锁者拿到锁后仍用旧缓存（xact.c:2483-2490 的注释）。
- 中止：只本地执行 PriorCmd，不广播（[[S11.M09]] Inv(3)）。

### P2 加锁查找与重查
1. `RangeVarGetRelidExtended`：按名查 OID；2. 加锁（期间接收失效）；3. 若 SharedInvalidMessageCounter 变了，重查名字，直到前后一致（file:src/backend/catalog/namespace.c:469-474,583-592）。
- 省掉第 3 步：取到的是已被改名或删除的对象的锁。计划缓存的对应做法是加锁后复查 is_valid（file:src/backend/utils/cache/plancache.c:746）。

### P3 inplace 更新（非事务性）
1. `heap_inplace_lock` 持元组锁并预登记失效（`CacheInvalidateHeapTupleInplace`，file:src/backend/access/heap/heapam.c:6620）。
2. `PreInplace_Inval`：临界区外删 init file（可能失败，故放在此处）（heapam.c:6767；inval.c:1244-1252）。
3. 临界区：写带失效消息的 WAL → 改页 → 放 buffer 锁 → `AtInplace_Inval` 发 SI → END_CRIT（heapam.c:6795-6852）。
4. 放元组锁 → 本地 Accept → 再登记一份事务性失效供逻辑解码和第三方代码使用（heapam.c:6853-6863）。
- I4.R5 在第 3 步之后成立。`SearchSysCacheLocked1` 依赖"放元组锁之前已发 SI"：它取元组锁后 Accept（file:src/backend/utils/cache/syscache.c:340-362）。把发送挪到放元组锁之后，读者可能取锁后仍拿到旧行；只登记事务性失效，回滚时失效丢了而 inplace 结果还在（commit:243e9b40f1b）。

### P4 relcache init file
1. 提交方：取 RelCacheInitLock → 删 init file → 发 SI → 放锁。2. 写 init file 的后端：写临时文件 → 取 RelCacheInitLock → Accept → 期间收到过 relcache 失效就丢弃临时文件，否则 rename（file:src/backend/utils/cache/relcache.c:6870-6890,6958-6975）。3. 启动的后端先 `SharedInvalBackendInit`，再读 init file（file:src/backend/utils/init/postinit.c:761,867）。
- 颠倒 1 的前两步：启动中的后端可能读到旧文件又漏掉消息。

### P5 带重试的缓存构建
1. 构建前把条目压入进行中栈（relcache 的 in_progress_list，catcache 的 CatCInProgress）（file:src/backend/utils/cache/relcache.c:162-175；file:src/backend/utils/cache/catcache.c:52-58）。
2. 构建中任何 Accept 若命中栈上的条目，就标记它失效。
3. 构建结束时看到标记就重来；catcache 在 detoast 之后用 `systable_recheck_tuple` 复查（commit:ad98fb14226）。
- I4.R7 在第 3 步之后成立。没有第 1 步的缓存（多数高层缓存）只能靠 DDL 的强锁（[[X73]]）。

### P6 队列溢出与重置
1. 写者插入前若队列将满，`SICleanupQueue` 把最落后的后端置 resetState，并向接近落后的后端发 catchup 信号（file:src/backend/storage/ipc/sinvaladt.c:44-55）。2. 被重置的后端下次接收时调 `InvalidateSystemCaches`：catcache 全清 → relcache（先更新 mapped 关系的 relfilenumber，再 nailed，再其他）→ 调全部回调（file:src/backend/utils/cache/inval.c:783-789；file:src/backend/utils/cache/relcache.c:2995）。3. 空闲在事务外的后端收到 catchup 时开关一个空事务来接收（file:src/backend/storage/ipc/sinval.c:175-200）。
- 回调把"全部失效"当成空操作，就会在重置后永远保留旧条目（commit:7f481b8d388）。

### P7 备库重放
xact_redo_commit：写 clog → 更新 KnownAssignedXids → `ProcessCommittedInvalidationMessages` → 释放代持的 AEL（file:src/backend/access/transam/xact.c:6264-6292）。先放锁后发失效，备库查询会在新取的锁下用旧缓存。

## 5. 并发与失败语义
- error：中止只本地执行 PriorCmd 消息，清掉本事务装入的条目；子事务中止就地处理（[[S11.M09]] Inv(3)）。relcache 重建出错时条目保持 !rd_isvalid，下次再建（[[S11.M07]] Inv(2)）。高层缓存出错的回滚语义"未定义"（[[S11.M10]] Contract）。提交时 ProcArrayEndTransaction 之后的出错已无法中止（[[S07.M01]] Contract），所以发送失效不能出错；inplace 与 relmap 的发送在临界区内，失败即 PANIC（I4.R5）。
- crash：sinval 队列、所有缓存都不持久，随整体重置丢弃；init file 缺失或损坏即重建（[[S11.M07]] Contract）。提交记录和 inplace 记录携带失效消息，供备库和解码使用。
- cancel：同 error；提交与中止清理期间 HOLD_INTERRUPTS（[[S07.M01]] Contract）。plancache 的 cancel 语义卡片标"假设"。
- standby：失效由重放提交记录产生（P7，I4.R16）；备库只代持 AEL，所以只有在主库取 AEL 的变更才能保证备库查询看不到中间状态（[[S11.M12]] Inv(A3)）。[[S11.M04]]、[[S04.M09]]、[[S10.M12]]、[[S10.M15]] 的 standby 项卡片标"未定义"；[[S02.M06]] 标"假设"。

## 8. 校验手段
- `debug_discard_caches`（assert 构建默认可用）：在每个可能接收失效的点强制清空 syscache/relcache/relsynccache，能暴露"在 Accept 点之后继续用缓存指针"和回调处理不当（I4.R6、I4.R8）；查不出漏登记的失效（I4.R3），因为它清得比真实情况多（file:src/include/pg_config_manual.h:288-292；file:src/backend/utils/cache/inval.c:947-972；commit:3d65b0593c5 就是这样发现的）。
- `CATCACHE_FORCE_RELEASE`、`RELCACHE_FORCE_RELEASE` 编译宏：引用计数归零即释放，暴露释放后使用和 reload 路径缺字段（commit:b82c877e76e 由此发现）。
- catcache 的 assert 构建以约千分之一概率假装复查失败，使重试路径在回归测试中被走到（file:src/backend/utils/cache/catcache.c:2182-2187；commit:ad98fb14226）。只覆盖 catcache 的构建重试（I4.R7）。
- isolation 测试 `inplace-inval`、`intra-grant-inplace`、`intra-grant-inplace-db`：覆盖 inplace 更新与失效的交错（file:src/test/isolation/isolation_schedule:50-52）（I4.R5）。
- `AtInplace_Inval`/`PreInplace_Inval` 断言是否在临界区内（file:src/backend/utils/cache/inval.c:1250,1260）；`relation_open(NoLock)` 断言调用者已持锁（file:src/backend/access/common/relation.c:67-70）（I4.R2 的一部分）。
- 只靠约定、没有机械检查：I4.R3（哪些 DDL 需要显式 relcache 失效，[[X10]]）；I4.R9（高层缓存是否注册了全部依赖）；I4.R7 对多数高层缓存（[[X73]]）；I4.R11；已持锁不接收失效的缺口（[[X72]]）；I4.R17 的分发完整性。
