## 设计原因（决策）
- D-plancache-lazy-inval {[[F4]] [[F1]]} 计划失效采用"sinval 标记 + 下次使用时惰性重做"，只对 relation/函数/类型精确跟踪，其他目录全量失效 ← 原始: 未考证；当前: 这些目录很少变，精细跟踪不值得〔file:src/backend/utils/cache/plancache.c:14,36〕
- D-plancache-generic-custom {[[F4]] [[F7]]} plancache 同时承担 generic/custom 计划选择，先建机制、策略可替换 ← 原始: 让缓存计划能生成依参数值定制的计划，并在 custom 与 generic 间做选择；该提交只建机制不定策略〔commit:e6faf910d75〕；当前: 选择逻辑集中在 choose_custom_plan〔file:src/backend/utils/cache/plancache.c:6-11〕
- D-sqlfunc-plancache {[[F4]]} SQL 函数改用 plancache，从而得到 custom 计划、跨外层查询复用，并使旧式 SQL 函数内的 DDL 能影响后续语句（新式 SQL 函数基本仍不能，其分析结果已固化在存储的查询树中） ← 原始: 旧实现只在一次外层查询内复用计划，且不能按参数值定制〔commit:0dca5d68d7b〕
- D-proto-whole-message {[[F1]]} 出站消息只能整条发送 ← 原始: 未考证；当前: ERROR 中途中断不会让通道卡在半条消息上〔file:src/backend/libpq/pqcomm.c:11〕
- D-proto-minor-negotiation {[[F5]]} minor 协议版本与 `_pq_.` 选项走协商而不是硬失败 ← 原始: 新 minor 版本与新选项无需重连即可与旧服务器共存〔commit:ae65f6066dc〕
- D-notify-slru-queue {[[F4]]} LISTEN/NOTIFY 从 pg_listener 表改为单一 SLRU 队列，不写 WAL、重启即清空 ← 原始: 比旧实现高效得多，且更兼容 Hot Standby〔commit:d1e027221d0〕；当前: 单队列保证按提交顺序收到；通知不需跨崩溃保留，故重启即清空、无需 WAL 与 fsync〔file:src/backend/commands/async.c:21-22,24-25,34-36,850〕
