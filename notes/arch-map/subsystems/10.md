# S10 复制（Tier A）
Secret: 主库 WAL 如何离开本机（物理流、逻辑解码）、哪些保留义务压住 WAL 回收与 vacuum（slot）、订阅端如何把远端变更原子地落到本地（apply + origin）。
边界: `replication/pgrepack/` → [[S06]]；`executor/execReplication.c`（apply 用的单行 DML）→ [[S05]]；WAL 读写与 redo 本身 → [[S09]]；
`access/heap/heapam_visibility.c` 的 `HeapTupleSatisfiesHistoricMVCC` → [[S06]]；procarray 视界、`storage/ipc/standby.c` 冲突、`xact.c` 把 origin 写进 commit 记录 → [[S07]]。

## 设计原因（决策）
- D-physical-rep-ships-wal {[[F1]] [[F7]]} 内建复制传送 WAL 给备库重放 → 基础性决策，完整记录见 principles.md 的 [[D-physical-rep-ships-wal]]
- D-replication-slot {[[F1]]} 引入 slot：用崩溃安全的结构阻止过早回收 WAL 和过早剪枝元组，取代旧做法；不放 catalog，因为要能在 standby 上分配 ← 原始: 崩溃安全、可在主或备上创建，防止过早删除 WAL 与（配合 hot_standby_feedback）过早剪枝〔commit:858ec11858a〕；当前: 要持久、崩溃安全且可在 standby 上分配，所以不能放 catalog〔file:src/backend/replication/slot.c:15-21〕
- D-logical-decoding-on-wal {[[F3]]} 逻辑解码建在 WAL 上 → 基础性决策，完整记录见 principles.md 的 [[D-logical-decoding-on-wal]]
- D-origin-progress-in-commit {[[F1]] [[F4]]} apply 用 origin 记进度：进度随本地 commit 记录写入 WAL，崩溃后可精确恢复，同时允许异步提交，让单线程回放跟上多后端源 ← 原始: 安全地跟踪进度并按 origin 过滤；放在"用户态"表里更低效、更复杂〔commit:5aa2350426c〕；当前: commit 记录带远端 LSN，崩溃后可精确恢复而无需同步提交，单线程回放能跟上多后端源〔file:src/backend/replication/logical/origin.c:26-36〕
- D-syncrep-primary-decides {[[F1]] [[F7]]} 同步复制决策只在主库：standby 不感知事务持久性需求，不传事务状态 ← 原始与当前: 不收发事务状态信息，减少簿记开销；等待与释放逻辑全在主库，standby 更简单〔commit:a8a8a3e0965; file:src/backend/replication/syncrep.c:14-20〕
- D-tablesync-per-table {[[F4]]} 初始同步按表分 worker：可以并行，不必为整库长期持有 xid/LSN，并能接纳后加的表 ← 原始: 未考证；当前: 可以并行、减少膨胀与磁盘占用、可接纳后加的表〔file:src/backend/replication/logical/tablesync.c:19-27〕
